## 网络中连接的建立

这里讨论CS模式中,网络连接的建立

**连接建立**：客户端通过网络连接到服务器 这个过程发生什么?

介绍相关概念和技术,并举一个例子

连接建立本质上是：**客户端（client）和服务器（server）为了能够相互通信，必须先协商一条可靠、可识别、可交换数据的通道**。

------

## 网络层的基本概念

在真正“建立连接”前，有一些背景概念必须清楚。

- **IP 地址（IP address）**：网络中设备的“地址”，用于找到对方。
- **端口号（port）**：设备上提供不同服务的入口。例如 Web 服务通常使用端口 80 或 443。
- **套接字（socket）**：客户端使用“**IP + 端口**”创建一个类似“通信插口”的对象(`IP:PORT`)。

这些概念共同确保客户端能准确定位服务器上的正确服务。

------

### 传输层：TCP 连接建立（三次握手 Three-way Handshake）

TCP（Transmission Control Protocol）是一种**面向连接（connection-oriented）**的**可靠传输协议**。当我们说“建立连接”，通常就是指 TCP 进行的三次握手。

整个过程确保双方 **都有发送与接收能力**，并且 **初始序列号（Sequence Number）** 达成一致，从而保证消息顺序可靠。

三次握手流程：

1. **SYN**：客户端发送一个带 SYN (**Synchronize** )标志的包（SYN packet），告诉服务器“我想建立连接”。
2. **SYN + ACK**：服务器回复一个包含 SYN 与 ACK(**Acknowledgment** ) 的包，表示“我收到了你的请求，并同意建立连接”。
3. **ACK**：客户端发送 ACK，确认服务器的回应。此时连接建立完成。

此时双方都拥有一个 TCP 连接状态，进入可传输数据的阶段。



SYN 和 ACK 是 TCP 协议中两个重要的标志位缩写：

#### SYN

**SYN = Synchronize (同步)**

- **作用**：用于建立 TCP 连接时的同步操作( **synchronize sequence numbers**)
- **使用时机**：在三次握手的第一次和第二次握手时使用
- **标志位设置**：SYN=1 表示这是一个连接建立请求
- **序列号**：发送 SYN 时会同时发送初始序列号

#### ACK

**ACK = Acknowledgment (确认)**

- **作用**：确认已收到的数据
- **使用时机**：确认任何收到的数据时使用
- **标志位设置**：ACK=1 表示确认号字段有效
- **确认号**：ACK 标志位为 1 时，确认号字段表示期望收到的下一个序列号

#### 在三次握手中的作用

第一次握手

```
客户端 → 服务器：SYN, Seq=X
```

- 只设置 SYN 标志位
- 发送**初始序列号** X

第二次握手

```
服务器 → 客户端：SYN-ACK, Seq=Y, Ack=X+1
```

- 同时设置 SYN 和 ACK 标志位
- 发送客户端自己的序列号 Y
- 确认序列号 X

第三次握手

```
客户端 → 服务器：ACK, Seq=X+1, Ack=Y+1
```

- 只设置 ACK 标志位
- 确认服务器的序列号 Y

SYN 专门用于连接的初始化同步，而 ACK 用于确认收到的数据，这两个标志位配合完成 TCP 可靠连接建立的核心机制。

------

### 更高层的协商（以 HTTP 为例）

连接建立后，应用层协议开始工作。

以 HTTP 为例：

- 客户端发送 **HTTP 请求（ HTTP request）**，例如 `GET /index.html`。
- 服务器处理后返回 **HTTP 响应（HTTP response）**，例如网页内容。

这一步已经是在连接建立之后的通信内容。

------

### 现实例子：浏览器访问一个网站

假设你在浏览器中输入：

```
https://example.com
```

实际发生的步骤如下：

1. **DNS 查询（DNS lookup）**
   浏览器先把 `example.com` 解析成服务器 IP，例如 `93.184.216.34`。

2. **客户端发起连接**
   客户端向该 IP(服务器) 的 443 端口发送 TCP SYN 数据包。

3. **服务器回应**
   服务器返回 SYN+ACK，客户端再发 ACK，完成 TCP 三次握手。

4. **TLS 握手（HTTPS 才有）**
   浏览器与服务器交换证书、公钥等信息，建立安全加密通道。
   关键词：

   - 证书（certificate）
   - 公钥加密（public key encryption）
   - 会话密钥（session key）

5. **客户端发送 HTTP 请求**
   如：

   ```
   GET / HTTP/1.1
   Host: example.com
   ```

6. **服务器返回页面**
   返回 HTML、CSS、JS 等内容，浏览器开始渲染。

整个流程中，真正的“连接建立”就是 **TCP 三次握手 +（如果使用 HTTPS）TLS 握手**。

------

### 小型代码示例（Python）

下面是一个非常简化的例子，展示客户端如何使用 socket 建立 TCP 连接：

```python
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(("example.com", 80))  # 建立 TCP 连接
client.send(b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n")
response = client.recv(1024)
print(response)
```

这里 `connect()` 调用触发的，就是 TCP 三次握手。



## 关于端口

### 端口是什么

“端口”（port）可以理解为：**一台机器上不同网络服务的入口编号**。
 英文常用解释是 *“logical communication endpoint”*（逻辑通信端点）。

一台机器可能同时运行多个**网络服务**，例如：

- Web 服务（HTTP/HTTPS）
- 数据库（MySQL/PostgreSQL）
- SSH 登录服务
- FTP、Redis、Nginx、游戏服务器等

如果只有 IP 地址，那么所有服务都挤在同一个入口，无法区分谁是谁。
 因此需要 **端口号 port number** 来区分不同的服务。

------

### 端口的范围

端口号是一个 **16 位无符号整数（unsigned 16-bit integer）**：

```
0 ~ 65535
```

不同区间有不同含义：

| 范围        | 名称（英文）                 | 说明                                             |
| ----------- | ---------------------------- | ------------------------------------------------ |
| 0–1023      | well-known ports（知名端口） | 由重要服务占用，需要管理员权限才能绑定           |
| 1024–49151  | registered ports（注册端口） | 各软件或组织申请使用,一半是服务端口,也称远程端口 |
| 49152–65535 | ephemeral ports（临时端口）  | **客户端**自动分配用于短期连接(客户端口)         |



------

### 为什么客户端也有端口？

常见误区：

> 端口只是服务器需要的，客户端不需要。

实际上，**客户端在发起连接时也需要一个临时端口（ephemeral port）**。
 例如客户端访问 MySQL 时的四元组（four-tuple）：

`local address:local port-> remote address:remote port`

```
客户端IP : 客户端端口  →  服务器IP : 服务端口
```

客户端端口由系统临时分配，用来区分不同连接，例如：

```
192.168.1.100:53124 → 10.0.0.8:3306
```

这样同一台机器可以同时打开多个到同一 MySQL 服务器的连接，因为端口不同。

### 端口名称

客户端口也称本地端口(local port)

服务端口也称远程端口(remote port)

注意对于一个连接,决定local port的机器和决定remote port的机器可能是同一台机器,或同一个ip,尤其是测试或学习环境下

如果是上了公网的生产环境,则连接的两端设备通常不同

### 端口查看工具

windows上有tcpview这个工具可以帮助我们方便地查看某个端口被什么进程占用,或者某个程序或进程占用什么端口

并且可以显示每个连接的端口情况,包括某个连接的客户端口(临时)和服务端口(长期)



------

### TCP 端口 vs UDP 端口

端口本身与协议无关，但它们**同时用于 TCP 与 UDP**：

- TCP 使用端口管理连接（connection）
- UDP 使用端口管理数据报（datagram）

例如：

| 协议 | 端口     | 服务         |
| ---- | -------- | ------------ |
| TCP  | 22       | SSH          |
| TCP  | 80 / 443 | HTTP / HTTPS |
| TCP  | 3306     | MySQL        |
| UDP  | 53       | DNS          |
| UDP  | 123      | NTP          |

------

### 一个形象的比喻

可以把 **IP 看成一栋大楼**，把 **端口看成楼里的房间号**。

- 大楼（IP）只有一个地址
- 房间号（端口）区分不同功能区
- 当快递送来时（网络数据），必须同时知道大楼地址和房间号才能送对地方

于是网络通信就依赖：

```
IP 地址 + 端口号 = 套接字（socket）
```

这是精确投递的关键。

------

### 端口为什么重要？

端口控制着设备上哪些服务暴露到网络。

端口开放意味着：

- 防火墙（firewall）必须放行
- 服务在监听该端口（listening）
- 可能被攻击者扫描探测（port scan）

典型安全策略是：

- **最小开放原则（principle of least privilege）**
- 只开放业务需要的端口
- 其他全部关闭或限制访问

例如生产环境常见：

| 服务       | 默认端口 | 建议策略                 |
| ---------- | -------- | ------------------------ |
| SSH        | 22       | 限制 IP、使用公钥登录    |
| MySQL      | 3306     | 不对公网开放，仅内网访问 |
| Web 服务器 | 80/443   | 对公网开放               |

------

### 用一个例子串起来

假设你执行：

```
mysql -h 10.0.0.8 -u root -p
```

系统建立连接时使用的四元组类似于：

```
客户端 192.168.1.100:52388 → 10.0.0.8:3306
```

52388 是临时端口（ephemeral port）
 3306 是 MySQL 服务端口（server port）

只有四元组唯一时，操作系统内核才能正确路由每条数据。

## 更多网络连接应用案例

------

下面以 **MySQL 客户端连接数据库** 和 **SSH 客户端连接服务器** 为例，分别说明“连接建立”过程中到底发生了什么。解释会包含关键概念的英文注释（例如 authentication、handshake），并用表格区分两者的差异。

------

### MySQL 客户端连接数据库的过程

当你执行：

```
mysql -h 10.0.0.8 -u root -p
```

背后的步骤如下。

#### TCP 层建立连接

MySQL 使用 **TCP 3306 端口**（默认）。
 客户端向服务器发起 TCP 三次握手（three-way handshake）：

- SYN
- SYN + ACK
- ACK

连接建立后，TCP 通道就准备好了。

#### MySQL 专有握手（MySQL Handshake）

与 HTTP 不同，MySQL 在 TCP 之上还有自己的**应用层握手协议（application-layer handshake）**。

流程如下：

1. **服务器先发送握手包（Handshake Packet）**
   包含：

   - 协议版本（protocol version）
   - 服务器能力标志（capability flags）
   - 随机盐值（salt，用于密码加密）
   - 字符集编码（character set）
   - 服务版本号

   这是 MySQL 的特点：一次连接中(TCP通道就绪后)，由**服务器先说话**。

2. **客户端发送登录请求（Login Request）**
   内容包括：

   - 用户名（username）
   - 加密后的密码（password hash）
   - 想要使用的数据库（schema）
   - 客户端能力标志（capabilities）

3. **服务器进行认证（authentication）**
   比较密码哈希是否正确，检查权限。

4. **服务器返回 OK 包（OK Packet）或 ERR 包**

   - OK → 登录成功
   - ERR → 登录失败

#### 连接建立后的状态

当 MySQL 客户端看到：

```
Welcome to the MySQL monitor...
```

说明：

- TCP 已建立
- MySQL 认证已通过
- 应用层会话已进入可交互状态

你可以发送 SQL 查询，例如：

```
SELECT NOW();
```

服务器解析、执行并返回结果。

------

### SSH 客户端连接服务器的过程

假设你执行：

```
ssh user@192.168.1.20
```

SSH 的连接建立过程比 MySQL 复杂得多，因为它承担了**安全加密、安全认证、密钥交换**等功能。

#### TCP 层连接

SSH 默认使用 **TCP 22 端口**。
 同样先进行 TCP 的三次握手。

#### SSH 协议层握手（SSH Handshake）

主要包含：

1. **版本交换（version exchange）**
   双方先各发送一行字符串，例如：

   ```
   SSH-2.0-OpenSSH_9.0
   ```

2. **算法协商（algorithm negotiation）**
   协商的内容包括：

   - 加密算法（encryption algorithm）
     如 `aes256-gcm`
   - 密钥交换算法（key exchange algorithm）
     如 `curve25519-sha256`
   - MAC 校验算法（message authentication code）
   - 压缩算法（compression）

   这是 SSH 安全性的重要基础。

3. **密钥交换（key exchange）**
   使用 Diffie–Hellman 或 Curve25519 交换随机数，生成会话密钥（session key）。
   此后通信全程加密。

#### 用户认证（user authentication）

SSH 支持多种认证方法：

- 密码（password）
- 公钥认证（public key authentication）
- 多因素认证（MFA）

如果使用公钥认证：

1. 客户端告诉服务器它要使用某个公钥（public key）。
2. 服务器发送 challenge（挑战）。
3. 客户端用私钥（private key）签名挑战内容。
4. 服务器验证签名 → 完成认证。

认证成功后，就进入可交互状态。

#### 打开会话通道（session channel）

SSH 的连接内部可以开多个“通道（channel）”，你看到的命令行其实是一个“会话通道”。

连接建立后，你会看到：

```
[user@server ~]$
```

------

### MySQL 与 SSH 连接建立流程对比

| 项目                       | MySQL                  | SSH                         |
| -------------------------- | ---------------------- | --------------------------- |
| 默认端口（port）           | 3306                   | 22                          |
| TCP 握手                   | 有                     | 有                          |
| 应用层握手（handshake）    | MySQL 专用握手         | SSH 安全握手（含算法协商）  |
| 身份认证（authentication） | 用户名 + 密码（hash）  | 密码、公钥、多因素          |
| 加密（encryption）         | 默认无加密（除非 SSL） | 强制加密                    |
| 连接后本质                 | 发送 SQL 命令          | 进入 Shell 会话，可执行命令 |
| 谁先发送握手包             | 服务器先发             | 双方互发版本 → 然后协商算法 |
