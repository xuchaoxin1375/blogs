## 为什么先分清文档类型

你可能见过这样的“入门教程”：开头先讲产品历史和技术架构，接着列出所有参数，然后给出几十个操作步骤，最后附上一大段设计哲学。读到一半，你已经不知道自己是在学习、在查资料，还是在完成一项任务。

问题往往不在文笔，而在于**四种不同的读者需求被塞进了同一篇文档**。

**Diátaxis** 是一种帮助作者区分这些需求的方法。它把技术文档分成四种基本类型：教程、操作指南、参考和解释。它的核心主张是：**不同类型的文档回应不同需求，应该用不同方式写。** [来源：Diátaxis：Start here](https://diataxis.fr/start-here/)

> **Diátaxis** **没有官方的中文称呼**。在中文技术文档社区中，它通常直接保留英文原名“Diátaxis”来使用。
>
> - **直接使用原名**：绝大多数技术文章和文档框架介绍中，会直接写作“Diátaxis 框架”。根据其英语发音大致可译为“**迪亚塔克西斯**”，但这并非通用叫法，不建议在正式材料中使用。
> - **意译描述**：有人会依据其词源（古希腊语中意为“安排、布置”）或核心理念，将其理解为一种“**系统化文档写作方法**”或“**文档四象限框架**”，但这属于解释性描述，并非固定译名。

本文面向第一次接触 **Diátaxis** 的文档作者，用尽量少的术语说明四类文档的**区别、适用场景、常见误区和选择方法**。文中的例子为说明用法而设计，不是 Diátaxis 官方示例。

## 四类文档，四种需求

### 两个维度：行动与认知，学习与工作

Diátaxis 用两个维度理解文档：

- **行动与认知**：读者是要“做什么”，还是要“知道什么”？
- **学习与工作**：读者是在“学习或获取技能”，还是在“工作或应用技能”？

把两个维度交叉，就得到四类文档：

| 读者状态 | 指导行动 | 提供认知 |
| --- | --- | --- |
| **学习或获取技能** | 教程 | 解释 |
| **工作或应用技能** | 操作指南 | 参考 |

这张表对应 Diátaxis 的核心地图。它不是按文档长短、难度或格式分类，而是**按读者此刻的需求分类**。

可以进一步记住两句话：

- **教程和操作指南都指导行动**，但教程服务学习，操作指南服务工作。
- **参考和解释都提供认知**，但参考服务工作，解释服务学习；参考描述事实，解释连接背景和原因。

如果你不确定该写哪一种，先问两个问题：读者是在学习还是在工作？读者需要行动还是认知？答案会把你带到四类中的一类。

### 教程：带读者学会一件事

**教程**(Tutorial)是一堂课，带读者在受控环境中完成一次有意义的实践。它始终是**学习导向**(learning-oriented)的，重点不是帮读者完成工作，而是让读者通过做来获得技能和信心。[来源：Diátaxis：Tutorials](https://diataxis.fr/tutorials/)

教程的读者可能还**提不出正确的问题**。他们需要作者替他们选择一条可靠路径，告诉他们在哪里做、做什么、会看到什么。

一个好的教程通常具备：

- 一个具体、可见的最终成果。
- 一条受控的主线，不要求读者做技术选型。
- 每一步都有可观察的结果和检查点。
- 失败可以安全重试，不会造成不可恢复的后果。
- 解释只保留当前动作所需的最低限度。

例子：**用Python做一个猜数字游戏**。读者跟着做，最后看到一个能运行的小游戏，并在过程中熟悉变量、输入、条件判断和循环。

教程不应该成为：

- 完整参数表。
- 多种方案的比较。
- 长篇架构历史。
- 让读者自行判断的复杂分支。

一句话：**教程对“学会”负责，不对“完成实际工作”负责。**

### 操作指南：帮读者把事做成

**操作指南**(How-to Guide)面向一个真实世界的问题或目标，提供可执行的行动方向。它始终是**任务导向**(task-oriented)的，服务的是读者的工作，而不是学习。[来源：Diátaxis：How-to guides](https://diataxis.fr/how-to-guides/)

操作指南假设读者**已经具备基本能力**，知道自己想做什么，也能理解基本术语。作者不需要从零教学，而要把注意力放在任务的条件、步骤、分支、验证和失败处理上。

一个好的操作指南通常具备：

- 一个明确的任务标题，例如“如何为GitHub仓库配置域名级代理”。
- 适用条件和前置假设。
- 按真实工作顺序组织的步骤。
- 必要的分支：如果A，就这样；如果B，就那样。
- 每一步的验证方法。
- 常见失败的原因和恢复方式。

例子：**如何撤销一次已经推送的提交**。读者已经会用Git，现在遇到一个具体问题；指南应比较`reset`、`revert`等方案的适用条件，给出推荐路径和风险。

操作指南不应该成为：

- 从零解释版本控制是什么。
- 完整命令参考。
- 长篇设计哲学。
- 只适用于作者自己环境的唯一做法。

一句话：**操作指南对“把事做成”负责，不对“教会读者”负责。**

### 参考：让读者查得准

**参考**(Reference)是对系统、接口、参数、规则的技术描述。它始终是**信息导向**(information-oriented)的，服务读者在工作中的查阅需求。[来源：Diátaxis：Reference](https://diataxis.fr/reference/)

参考的读者不是从头读到尾的。他们带着一个具体问题来，希望快速找到准确、完整、可信的答案。参考应该像地图：结构反映产品本身的结构，格式稳定，便于定位。

一个好的参考通常具备：

- 准确、完整、无歧义的事实。
- 与产品结构一致的层级和命名。
- 统一的字段、参数、返回值、错误码格式。
- 简短的用法示例。
- 明确的限制、默认值和版本差异。

例子：**`git reset`命令参考**。它应列出语法、参数、默认行为、常见组合、限制和版本差异，而不是讲一个“我是如何学会Git”的故事。

参考不应该成为：

- 教程叙事。
- 主观推荐。
- 长篇原理讨论。
- 把操作步骤混进参数表。

一句话：**参考对“查得准”负责，不对“教得会”负责。**

### 解释：让读者想明白

**解释**(Explanation)是对主题的论述性说明，帮助读者建立背景、联系和判断力。它始终是**理解导向**(understanding-oriented)的，服务读者的学习，而不是直接指导工作。[来源：Diátaxis：Explanation](https://diataxis.fr/explanation/)

解释的读者想知道的不是“下一步点什么”，而是“为什么是这样”“它和别的东西有什么关系”“有哪些取舍”。解释可以包含观点、历史、替代方案和边界，它的价值在于把零散知识连接起来。

一个好的解释通常具备：

- 一个明确的“为什么”问题。
- 背景、动因和历史。
- 概念之间的关系。
- 不同方案的比较和取舍。
- 适用边界和反例。
- 必要时承认观点和局限。

例子：**为什么Git的分支如此轻量**。它可以从提交图、分支指针、历史模型讲起，解释这种设计与其它版本控制系统的差异，以及它带来的好处和代价。

解释不应该成为：

- 一步步的操作手册。
- 完整参数表。
- 只讲结论不讲背景。
- 为了显得高深而故意晦涩。

一句话：**解释对“想明白”负责，不对“马上做成”负责。**

## 最容易混淆的两类：教程与操作指南

教程和操作指南都包含步骤，看起来很像。这是软件产品文档中最常见的混淆之一。

为行文方便，下文用“指南”简称“操作指南”；中文语境里更宽泛的“指南”会在“标题叫教程，不一定是教程”中说明。

它们的区别不在“长短”或“难度”，而在读者此刻的需求：**是在学习，还是在工作。**

| 对比维度 | 教程 | 操作指南 |
| --- | --- | --- |
| **读者状态** | 学习，可能还提不出正确的问题 | 工作，已经知道自己要做什么 |
| **主要目的** | 获得技能和信心 | 完成一个具体任务 |
| **路径** | 作者精心设计的一条学习路径 | 面向真实问题的行动路径，可以有分支 |
| **对意外的态度** | 尽量消除意外，保证成功 | 准备意外，说明分支和恢复 |
| **责任** | 作者对学习体验负责 | 读者对自己的工作结果负责 |
| **环境** | 受控的练习环境 | 真实环境 |
| **典型标题** | 用Python做一个猜数字游戏 | 如何为GitHub仓库配置代理 |
| **不做什么** | 不堆参数、不比较所有方案 | 不从零教学、不写完整参考 |

**“教程一定简单，操作指南一定高级”是误解。**教程可以讲很高级的主题，操作指南也可以处理很基础的任务。区别在于：教程帮助读者**学习**，操作指南帮助读者**工作**。[来源：Diátaxis：教程与操作指南的区别](https://diataxis.fr/tutorials-how-to/)

### 适合与不适合的场景

把两类文档放到具体场景里，差异会更清楚。

| 维度 | 教程 | 操作指南 |
| --- | --- | --- |
| **读者起点** | 还不会，或需要建立基本能力 | 已具备基本能力，知道要完成什么 |
| **主要目标** | 获得技能与信心 | 完成一个具体任务 |
| **环境** | 受控、可重试的练习环境 | 真实环境，可能有后果 |
| **路径** | 作者设计的一条主线 | 面向现实条件的分支路径 |
| **失败处理** | 允许安全重试 | 需要风险说明、恢复和清理 |
| **成功标准** | 读者以后能独立完成同类任务 | 当前任务完成并验证 |
| **适合** | 第一次接触工具或概念；建立完整工作流；培训与上手 | 已会基本操作；解决明确问题；生产变更、迁移、排错 |
| **不适合** | 读者已会基本操作、只想完成当前任务；真实环境中的高风险不可逆操作；需要比较多个方案 | 读者还没有基本能力；需要从零建立心智模型；目标是系统理解原理 |

这张表不是给文档贴标签，而是帮助判断“错配”的代价。把真实任务塞进教程，会把风险和不必要的分支带给新手；把从零教学塞进指南，会让熟练读者在大量已知内容中找不到当前步骤。

### 学习与工作的判断边界

“学习”和“工作”不是按人的身份分的，也不是按主题难度分的，而是按读者此刻的主要义务分的。一个人可能一边工作一边学习；一篇教程也可能让读者完成一个小成果。判断边界时，看的不是“他是不是在学习”，而是“这篇文档主要承诺什么”。

| 判断问题 | 更偏教程 | 更偏指南 |
| --- | --- | --- |
| **读者现在能独立完成这件事吗？** | 不能，目标是建立能力 | 能，目标是完成当前任务 |
| **这次操作在什么环境？** | 练习、受控、可重试 | 真实、生产、有后果 |
| **失败后可以轻松重来吗？** | 可以 | 不一定，需要恢复方案 |
| **路径需要按现实条件分支吗？** | 不需要，作者替读者选 | 需要，按条件给不同路径 |
| **成功标准是什么？** | 读者以后能独立做 | 当前任务完成并验证 |

一句话：**学习是“为了以后能独立做”，工作是“现在就要做成”。**

两个常见误判：

- “我是新手，所以一定需要教程。”不一定。新手执行一个已经定义好的操作，也可能只需要一份写清楚前提的指南。
- “我是老手，所以不需要教程。”不一定。老手学新工具、新范式，仍可能需要教程来建立新的心智模型。

如果边界仍然模糊，用“主要义务”测试：**如果这篇文档失败，是读者没学会，还是任务没完成？**前者按教程设计，后者按指南设计。

这些区分来自 Diátaxis 对“学习”与“工作”的划分。[来源：Diátaxis：教程与操作指南的区别](https://diataxis.fr/tutorials-how-to/)

### 标题叫教程，不一定是教程

中文里，“教程”常被当作技术文档的泛称。博客、笔记、产品文档里，很多标题叫“教程”的内容，实际上是一份操作指南；也有标题叫“指南”的内容，实际上是从零带读的教程。

同样，中文的“指南”也比 Diátaxis 的操作指南(How-to Guide)更宽：它可能指操作指南、入门读物，甚至参考手册。不要按标题直接映射类型。

标题不能作为判断依据。判断一篇文档的实际类型，看四件事：

- 它假设读者已经会什么？
- 它把读者放在练习环境还是真实环境？
- 它给一条主线，还是按现实条件分支？
- 它的成功标准是“学会了”，还是“做成了”？

例如：

- 标题《Git 使用教程》，开头写“前提：已安装 Git 并会基本提交”，正文是“如何配置远程认证”——它实际上是指南。
- 标题《Git 配置指南》，却从安装开始，一步步带读者完成第一次提交并解释每个区域——它实际上是教程。

**不必强行改名，但要按主要义务设计结构。**命名可以宽泛，结构不能含糊。

## 为什么不能混在一起

把四类文档混在一起，通常会让每一类都变差：

- 教程里塞满参数和方案比较，初学者不知道哪些是必须的，要同时处理的信息过多。
- 操作指南里从零解释基础，熟练读者被迫跳过大量内容，找不到真正需要的步骤。
- 参考里夹叙夹议，读者无法快速扫描和定位事实。
- 解释里插入操作步骤，读者还没建立整体理解，就被细节打断。

更合理的做法不是“把所有内容删掉”，而是**把内容放到它该在的地方，再用链接连接起来**。教程可以留一句“这里用HTTPS是因为更安全”，然后链接到解释文档；操作指南可以留一句“完整参数见参考”，然后链接到参考页。

**混写不是丰富，而是让读者在同一页里不断切换阅读模式。**

现实中，很多博客和笔记确实同时承担一点教学和一点办事功能。完全禁止混合既不现实，也没必要。更可行的做法是：先确定这篇文档的**主要义务**，让主线服务主要读者；另一种需求用三种方式处理：

- 开头给“快速路径”，让已经会的人直接完成当前任务。
- 把必要的概念解释压缩成一句话，放在首次使用处。
- 把完整教学、完整参数或方案比较链接到独立文档。

**命名可以宽泛，结构不能含糊。**一篇文档可以叫“教程”，但如果它的主要读者是已经会基本操作的人，正文就应按指南组织，而不是硬塞一套入门课程。

## 如何判断该写哪一种

动笔前，先问读者此刻的问题，而不是先想“我要写一篇什么格式的文章”。

| 读者此刻的问题 | 更适合的类型 |
| --- | --- |
| 我还不会，能带我走一遍吗？ | 教程 |
| 我已经会基本操作，现在要完成这件事，怎么做？ | 操作指南 |
| 这个参数、字段或规则到底是什么意思？ | 参考 |
| 为什么这样设计？它和别的东西有什么关系？ | 解释 |

如果一个问题同时涉及多种需求，不要硬塞进一篇。可以拆成多篇，或者以一篇为主，把其他内容链接出去。

**同一主题可以有四种写法，因为它们回答的是四个不同的问题。**下面用 Git 做一个完整的判断示例。

## 案例：用 Git 管理代码仓库，该找教程还是指南？

“我要用 Git 管理代码仓库”是一个能力领域，不是一个具体的阅读需求。它没有说明你现在会不会、这次要在什么环境做什么、失败后能不能重来。所以不能直接回答“找教程”或“找指南”。

先把它改写成三个问题：

1. 我现在会不会 Git 的基本操作？
2. 我这次是要学会一套工作流，还是要完成一个具体任务？
3. 我是在练习仓库里做，还是在真实仓库里做？

根据答案，选择会不同。表中的文档标题是示意，用来说明不同类型的写法，不是现成文档。

| 你的处境 | 更适合 | 可以找的文档 | 原因 |
| --- | --- | --- | --- |
| 从没使用过 Git，不清楚工作区、暂存区、提交、分支是什么 | 教程 | 《用 Git 完成第一次提交与分支合并》 | 需要先建立基本心智模型和完整工作流；练习仓库允许安全试错 |
| 已经会 `add`、`commit`，第一次把本地仓库推到 GitHub | 操作指南 | 《如何把本地仓库推送到 GitHub》 | 已具备基本操作能力，当前目标是完成一个具体任务；重点是远程、认证、分支跟踪和验证 |
| 已经会基本操作，误提交了敏感文件，想撤销已推送的提交 | 操作指南 | 《如何撤销已推送的提交》 | 这是真实环境中的具体问题，有后果；需要比较 `reset` 与 `revert` 的适用条件、风险和恢复步骤 |
| 想理解 `merge` 与 `rebase` 的区别，以及团队该选哪种 | 解释 | 《merge 与 rebase：历史、取舍与适用边界》 | 目标是建立判断力，而不是马上执行一次操作；需要背景、比较和边界 |
| 要查 `git reset` 的参数、默认行为和版本差异 | 参考 | 《git reset 命令参考》 | 需要准确、完整、可定位的事实，不需要教学叙事 |
| 团队要制定分支策略并落地到仓库设置 | 解释 + 操作指南 | 《分支策略的取舍》+《为新仓库配置分支保护》（两篇，不是一篇混写） | 先用解释建立取舍，再用指南完成配置；两类内容分开，避免互相打断 |

这张表不是按“新手/老手”分的，而是按“当前任务”分的。一个从没用过 Git 的人，如果只是照着公司手册完成一次固定的发布操作，也可能只需要一份把前提写清楚的指南；他不必先学完整个 Git，但指南要列出所需的最小操作，并链接到教程。一个资深工程师第一次接触某种新的 Git 工作流，也可能需要一份教程。

**为什么这样分：**

- 教程的价值是“建立能力”。它控制变量、安排顺序、允许试错，让读者在练习中形成心智模型。它不要求读者先会 Git，但要求文档替读者做选择。
- 指南的价值是“完成当前任务”。它假设读者已经会基本操作，把篇幅放在真实条件、分支、风险、验证和恢复上。它不负责从零教学，但必须把前提写清楚。

用错类型不会让文档完全不可读，但会让读者付出额外成本：新手读指南，会在未声明的前提处卡住；熟手读教程，会在一遍遍基础解释中找不到自己需要的那一步。

**一个快速判断：**

- 第一次学 Git，想建立“提交—分支—远程”的整体认识：找教程。
- 已经会 `add`、`commit`，现在要把仓库推到 GitHub、撤销提交、配置代理：找指南。
- 想理解 `merge` 与 `rebase` 的取舍、Git 为什么这样设计：找解释。
- 要查某个命令的参数、默认值和版本差异：找参考。

**如果你只想记一句话：**

> 学习是“为了以后能独立做”，工作是“现在就要做成”。教程对“以后能独立做”负责，指南对“现在做成”负责。

最后，标题叫“教程”还是“指南”并不重要。重要的是它是否从你的起点开始，是否帮你完成当前目标。如果一篇“教程”开头就假设你会 `add` 和 `commit`，它实际上是一份指南；如果一篇“指南”从零带你做了一遍并解释每一步，它实际上是一份教程。

## 新手常见误区

| 误区 | 为什么有问题 | 更好的做法 |
| --- | --- | --- |
| **把教程写成百科** | 一开始讲完所有概念和参数，读者还没开始做就被淹没 | 只讲当前任务需要的，深入内容链接出去 |
| **把操作指南写成教程** | 从零解释基础，熟练读者找不到重点 | 假设基本能力，聚焦任务、分支、验证和恢复 |
| **把参考写成散文** | 参数表里夹故事和观点，读者无法快速查 | 只描述事实，统一格式，示例简短 |
| **把解释写成步骤** | 讲原理时插入操作，读者被细节打断 | 保持讨论性，连接概念，允许观点和替代方案 |
| **认为教程一定简单、参考一定高级** | 把类型和难度混为一谈 | 类型看读者需求，难度看主题和读者基础 |
| **按标题判断类型** | 叫“教程”的文档可能是指南，叫“指南”的可能是教程 | 看读者起点、环境、路径和成功标准 |
| **四种类型混在一页** | 读者不知道现在该读还是该做 | 分开写，用链接连接 |
| **只按产品功能分类** | 读者找不到“我想完成什么”的入口 | 同时按读者任务和问题组织 |

## 一个简单的写作流程

对新手来说，不必一次掌握全部理论。可以先按以下顺序练习：

1. **写一句读者问题**：读者此刻是在学习、工作、查阅，还是理解？
2. **选一个类型**：根据问题选择教程、操作指南、参考或解释。
3. **写一句目的**：这篇文档让读者能做什么、查到什么或理解什么？
4. **写一句边界**：这篇文档不做什么？
5. **按类型组织内容**：
   - 教程：目标、准备、受控步骤、检查点、迁移练习。
   - 操作指南：任务、前提、步骤、分支、验证、恢复。
   - 参考：结构、字段、参数、示例、限制。
   - 解释：问题、背景、关系、取舍、边界。
6. **检查是否混入其他类型的核心内容**：如果有，移到对应文档或链接出去。
7. **找一个目标读者试读**：看他是否知道自己在读什么、下一步做什么。

**先改一篇，不必一次改完整个文档库。**

## 初学者检查清单

- [ ] 我能用一句话说出这篇文档的类型和读者需求。
- [ ] 我能说出这篇文档的主要义务：让读者学会，还是帮读者做成。
- [ ] 我没有因为标题叫“教程”就把教学、任务、参考和原理都塞进同一篇。
- [ ] 教程有可见成果、检查点和安全重试。
- [ ] 操作指南有适用条件、步骤、验证和失败处理。
- [ ] 参考按产品结构组织，事实准确，格式一致。
- [ ] 解释围绕“为什么”，连接概念，承认替代方案。
- [ ] 我没有在一种文档里塞满另一种文档的核心内容。
- [ ] 我把深入内容链接出去，而不是全部塞进当前页。
- [ ] 我区分了“文档类型”和“内容难度”。
- [ ] 我找了一个目标读者试读，而不是只让专家审稿。

## Diátaxis是透镜，不是法条

Diátaxis 不是一套必须逐条执行的模板，也不是给文档贴标签的考试。它更像一副透镜：帮助你看见读者此刻的需求，以及文档中不协调的地方。

Diátaxis 的作者提醒读者：不需要读完整个网站才能开始使用；最好的开始方式，是拿一个小页面动手应用；你可以只取其中一个有用的想法，不必接受整套理论。[来源：Diátaxis：Start here](https://diataxis.fr/start-here/)

对新手来说，最实际的做法是：

1. 选一篇你正在写的文档。
2. 判断它主要服务哪一种需求。
3. 删掉或移走不属于这种需求的核心内容。
4. 给移走的内容找一个合适的去处。
5. 找一位目标读者试读。

**先让一篇文档的职责清楚，再逐步扩展到整个文档库。**
