## 为什么先分清文档类型

你可能见过这样的“入门教程”：开头先讲产品历史和技术架构，接着列出所有参数，然后给出几十个操作步骤，最后附上一大段设计哲学。读到一半，你已经不知道自己是在学习、在查资料，还是在完成一项任务。

问题往往不在文笔，而在于**四种不同的读者需求被塞进了同一篇文档**。

Diátaxis 是一种帮助作者区分这些需求的方法。它把技术文档分成四种基本类型：教程、操作指南、参考和解释。它的核心主张是：**不同类型的文档回应不同需求，应该用不同方式写。** [来源：Diátaxis：Start here](https://diataxis.fr/start-here/)

本文面向第一次接触 Diátaxis 的文档作者，用尽量少的术语说明四类文档的区别、常见误区和选择方法。文中的例子为说明用法而设计，不是 Diátaxis 官方示例。

## 四类文档，四种需求

### 两个维度：行动与认知，学习与工作

Diátaxis 用两个维度理解文档：

- **行动与认知**：读者是要“做什么”，还是要“知道什么”？
- **学习与工作**：读者是在“学习或获取技能”，还是在“工作或应用技能”？

把两个维度交叉，就得到四类文档：

| 读者状态 | 指导行动 | 提供认知 |
| --- | --- | --- |
| **学习或获取技能** | 教程 | 解释 |
| **工作或应用技能** | 操作指南 | 参考 |

这张表对应 Diátaxis 的核心地图。它不是按文档长短、难度或格式分类，而是按读者此刻的需求分类。

可以进一步记住两句话：

- **教程和操作指南都指导行动**，但教程服务学习，操作指南服务工作。
- **参考和解释都提供认知**，但参考服务工作，解释服务学习；参考描述事实，解释连接背景和原因。

如果你不确定该写哪一种，先问两个问题：读者是在学习还是在工作？读者需要行动还是认知？答案会把你带到四类中的一类。

### 教程：带读者学会一件事

**教程**(Tutorial)是一堂课，带读者在受控环境中完成一次有意义的实践。它始终是**学习导向**(learning-oriented)的，重点不是帮读者完成工作，而是让读者通过做来获得技能和信心。[来源：Diátaxis：Tutorials](https://diataxis.fr/tutorials/)

教程的读者可能还**提不出正确的问题**。他们需要作者替他们选择一条可靠路径，告诉他们在哪里做、做什么、会看到什么。

一个好的教程通常具备：

- 一个具体、可见的最终成果。
- 一条受控的主线，不要求读者做技术选型。
- 每一步都有可观察的结果和检查点。
- 失败可以安全重试，不会造成不可恢复的后果。
- 解释只保留当前动作所需的最低限度。

例子：**用Python做一个猜数字游戏**。读者跟着做，最后看到一个能运行的小游戏，并在过程中熟悉变量、输入、条件判断和循环。

教程不应该成为：

- 完整参数表。
- 多种方案的比较。
- 长篇架构历史。
- 让读者自行判断的复杂分支。

一句话：**教程对“学会”负责，不对“完成实际工作”负责。**

### 操作指南：帮读者把事做成

**操作指南**(How-to Guide)面向一个真实世界的问题或目标，提供可执行的行动方向。它始终是**任务导向**(task-oriented)的，服务的是读者的工作，而不是学习。[来源：Diátaxis：How-to guides](https://diataxis.fr/how-to-guides/)

操作指南假设读者**已经具备基本能力**，知道自己想做什么，也能理解基本术语。作者不需要从零教学，而要把注意力放在任务的条件、步骤、分支、验证和失败处理上。

一个好的操作指南通常具备：

- 一个明确的任务标题，例如“如何为GitHub仓库配置域名级代理”。
- 适用条件和前置假设。
- 按真实工作顺序组织的步骤。
- 必要的分支：如果A，就这样；如果B，就那样。
- 每一步的验证方法。
- 常见失败的原因和恢复方式。

例子：**如何撤销一次已经推送的提交**。读者已经会用Git，现在遇到一个具体问题；指南应比较`reset`、`revert`等方案的适用条件，给出推荐路径和风险。

操作指南不应该成为：

- 从零解释版本控制是什么。
- 完整命令参考。
- 长篇设计哲学。
- 只适用于作者自己环境的唯一做法。

一句话：**操作指南对“把事做成”负责，不对“教会读者”负责。**

### 参考：让读者查得准

**参考**(Reference)是对系统、接口、参数、规则的技术描述。它始终是**信息导向**(information-oriented)的，服务读者在工作中的查阅需求。[来源：Diátaxis：Reference](https://diataxis.fr/reference/)

参考的读者不是从头读到尾的。他们带着一个具体问题来，希望快速找到准确、完整、可信的答案。参考应该像地图：结构反映产品本身的结构，格式稳定，便于定位。

一个好的参考通常具备：

- 准确、完整、无歧义的事实。
- 与产品结构一致的层级和命名。
- 统一的字段、参数、返回值、错误码格式。
- 简短的用法示例。
- 明确的限制、默认值和版本差异。

例子：**`git reset`命令参考**。它应列出语法、参数、默认行为、常见组合、限制和版本差异，而不是讲一个“我是如何学会Git”的故事。

参考不应该成为：

- 教程叙事。
- 主观推荐。
- 长篇原理讨论。
- 把操作步骤混进参数表。

一句话：**参考对“查得准”负责，不对“教得会”负责。**

### 解释：让读者想明白

**解释**(Explanation)是对主题的论述性说明，帮助读者建立背景、联系和判断力。它始终是**理解导向**(understanding-oriented)的，服务读者的学习，而不是直接指导工作。[来源：Diátaxis：Explanation](https://diataxis.fr/explanation/)

解释的读者想知道的不是“下一步点什么”，而是“为什么是这样”“它和别的东西有什么关系”“有哪些取舍”。解释可以包含观点、历史、替代方案和边界，它的价值在于把零散知识连接起来。

一个好的解释通常具备：

- 一个明确的“为什么”问题。
- 背景、动因和历史。
- 概念之间的关系。
- 不同方案的比较和取舍。
- 适用边界和反例。
- 必要时承认观点和局限。

例子：**为什么Git的分支如此轻量**。它可以从提交图、分支指针、历史模型讲起，解释这种设计与其它版本控制系统的差异，以及它带来的好处和代价。

解释不应该成为：

- 一步步的操作手册。
- 完整参数表。
- 只讲结论不讲背景。
- 为了显得高深而故意晦涩。

一句话：**解释对“想明白”负责，不对“马上做成”负责。**

## 最容易混淆的两类：教程与操作指南

教程和操作指南都包含步骤，看起来很像。这是软件产品文档中最常见的混淆之一。

它们的区别不在“长短”或“难度”，而在读者此刻的需求：**是在学习，还是在工作。**

| 对比维度 | 教程 | 操作指南 |
| --- | --- | --- |
| **读者状态** | 学习，可能还提不出正确的问题 | 工作，已经知道自己要做什么 |
| **主要目的** | 获得技能和信心 | 完成一个具体任务 |
| **路径** | 作者精心设计的一条学习路径 | 面向真实问题的行动路径，可以有分支 |
| **对意外的态度** | 尽量消除意外，保证成功 | 准备意外，说明分支和恢复 |
| **责任** | 作者对学习体验负责 | 读者对自己的工作结果负责 |
| **环境** | 受控的练习环境 | 真实环境 |
| **典型标题** | 用Python做一个猜数字游戏 | 如何为GitHub仓库配置代理 |
| **不做什么** | 不堆参数、不比较所有方案 | 不从零教学、不写完整参考 |

**“教程一定简单，操作指南一定高级”是误解。**教程可以讲很高级的主题，操作指南也可以处理很基础的任务。区别在于：教程帮助读者**学习**，操作指南帮助读者**工作**。[来源：Diátaxis：教程与操作指南的区别](https://diataxis.fr/tutorials-how-to/)

## 为什么不能混在一起

把四类文档混在一起，通常会让每一类都变差：

- 教程里塞满参数和方案比较，初学者不知道哪些是必须的，要同时处理的信息过多。
- 操作指南里从零解释基础，熟练读者被迫跳过大量内容，找不到真正需要的步骤。
- 参考里夹叙夹议，读者无法快速扫描和定位事实。
- 解释里插入操作步骤，读者还没建立整体理解，就被细节打断。

更合理的做法不是“把所有内容删掉”，而是**把内容放到它该在的地方，再用链接连接起来**。教程可以留一句“这里用HTTPS是因为更安全”，然后链接到解释文档；操作指南可以留一句“完整参数见参考”，然后链接到参考页。

**混写不是丰富，而是让读者在同一页里不断切换阅读模式。**

## 如何判断该写哪一种

动笔前，先问读者此刻的问题，而不是先想“我要写一篇什么格式的文章”。

| 读者此刻的问题 | 更适合的类型 |
| --- | --- |
| 我还不会，能带我走一遍吗？ | 教程 |
| 我已经会基本操作，现在要完成这件事，怎么做？ | 操作指南 |
| 这个参数、字段或规则到底是什么意思？ | 参考 |
| 为什么这样设计？它和别的东西有什么关系？ | 解释 |

如果一个问题同时涉及多种需求，不要硬塞进一篇。可以拆成多篇，或者以一篇为主，把其他内容链接出去。

例如，“Git分支”可以拆成：

- 教程：用Git完成第一次分支合并。
- 操作指南：如何撤销一次已推送的提交。
- 参考：`git branch`与`git merge`命令参考。
- 解释：为什么Git的分支如此轻量。

**同一主题可以有四种写法，因为它们回答的是四个不同的问题。**

## 新手常见误区

| 误区 | 为什么有问题 | 更好的做法 |
| --- | --- | --- |
| **把教程写成百科** | 一开始讲完所有概念和参数，读者还没开始做就被淹没 | 只讲当前任务需要的，深入内容链接出去 |
| **把操作指南写成教程** | 从零解释基础，熟练读者找不到重点 | 假设基本能力，聚焦任务、分支、验证和恢复 |
| **把参考写成散文** | 参数表里夹故事和观点，读者无法快速查 | 只描述事实，统一格式，示例简短 |
| **把解释写成步骤** | 讲原理时插入操作，读者被细节打断 | 保持讨论性，连接概念，允许观点和替代方案 |
| **认为教程一定简单、参考一定高级** | 把类型和难度混为一谈 | 类型看读者需求，难度看主题和读者基础 |
| **四种类型混在一页** | 读者不知道现在该读还是该做 | 分开写，用链接连接 |
| **只按产品功能分类** | 读者找不到“我想完成什么”的入口 | 同时按读者任务和问题组织 |

## 一个简单的写作流程

对新手来说，不必一次掌握全部理论。可以先按以下顺序练习：

1. **写一句读者问题**：读者此刻是在学习、工作、查阅，还是理解？
2. **选一个类型**：根据问题选择教程、操作指南、参考或解释。
3. **写一句目的**：这篇文档让读者能做什么、查到什么或理解什么？
4. **写一句边界**：这篇文档不做什么？
5. **按类型组织内容**：
   - 教程：目标、准备、受控步骤、检查点、迁移练习。
   - 操作指南：任务、前提、步骤、分支、验证、恢复。
   - 参考：结构、字段、参数、示例、限制。
   - 解释：问题、背景、关系、取舍、边界。
6. **检查是否混入其他类型的核心内容**：如果有，移到对应文档或链接出去。
7. **找一个目标读者试读**：看他是否知道自己在读什么、下一步做什么。

**先改一篇，不必一次改完整个文档库。**

## 初学者检查清单

- [ ] 我能用一句话说出这篇文档的类型和读者需求。
- [ ] 教程有可见成果、检查点和安全重试。
- [ ] 操作指南有适用条件、步骤、验证和失败处理。
- [ ] 参考按产品结构组织，事实准确，格式一致。
- [ ] 解释围绕“为什么”，连接概念，承认替代方案。
- [ ] 我没有在一种文档里塞满另一种文档的核心内容。
- [ ] 我把深入内容链接出去，而不是全部塞进当前页。
- [ ] 我区分了“文档类型”和“内容难度”。
- [ ] 我找了一个目标读者试读，而不是只让专家审稿。

## Diátaxis是透镜，不是法条

Diátaxis 不是一套必须逐条执行的模板，也不是给文档贴标签的考试。它更像一副透镜：帮助你看见读者此刻的需求，以及文档中不协调的地方。

Diátaxis 的作者提醒读者：不需要读完整个网站才能开始使用；最好的开始方式，是拿一个小页面动手应用；你可以只取其中一个有用的想法，不必接受整套理论。[来源：Diátaxis：Start here](https://diataxis.fr/start-here/)

对新手来说，最实际的做法是：

1. 选一篇你正在写的文档。
2. 判断它主要服务哪一种需求。
3. 删掉或移走不属于这种需求的核心内容。
4. 给移走的内容找一个合适的去处。
5. 找一位目标读者试读。

**先让一篇文档的职责清楚，再逐步扩展到整个文档库。**

如果你想继续看教程和操作指南的具体写法、检查点设计和发布前检查清单，可以阅读[教程与指南写作指导](教程与指南写作指导.md)。
