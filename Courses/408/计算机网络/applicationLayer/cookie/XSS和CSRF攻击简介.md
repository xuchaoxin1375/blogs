在网络安全领域，XSS（跨站脚本攻击）和 CSRF（跨站请求伪造）是最常见的两种漏洞。虽然它们听起来很像，但原理和防御思路却大不相同。

简单来说：**XSS 窃取你的信任（盗取 Cookie），而 CSRF 利用你的信任（冒充你发请求）。**

- **XSS 骗的是浏览器**："这段脚本来自可信的网站，执行它吧。"
- **CSRF 骗的是服务器**："这个请求来自已经登录的用户，处理它吧。"

------

## 1. XSS (Cross-Site Scripting) —— 跨站脚本(攻击)

> 缩写`CSS`已经被**层叠样式表**(Cascading Style Sheets)占用,所以这里用`XSS`

**核心原理：** 攻击者通过在目标网站中注入**恶意脚本**（通常是 JavaScript），让这些脚本**在受害者的浏览器上执行**。

### 常见类型：

- **存储型 XSS：** 恶意代码被持久化存储在服务器数据库中（如评论区、个人资料）。每个访问该页面的用户都会中招。
- **反射型 XSS：** 恶意代码通过 URL 参数传递。攻击者诱骗用户点击一个带有恶意参数的链接（如 `[http://site.com?search=](http://site.com?search=)<script>alert('XSS')</script>`）。
- **DOM 型 XSS：** 纯前端漏洞，通过修改页面的 DOM 环境来触发执行，不经过服务器。

### 攻击后果：

- 窃取用户的 **Cookie** 或 Session Token。
- 劫持用户会话，进行非法操作。
- 篡改页面内容或强制跳转到钓鱼网站。

### 防御方案：

- **输入过滤与输出转义：** 对用户提交的所有内容进行严格检查，并在展示时进行 HTML 转义（如将 `<` 转为 `<`）。
- **开启 HttpOnly：** 在 Cookie 中设置 `HttpOnly` 标识，防止 JS 脚本读取 Cookie。
- **内容安全策略 (CSP)：** 通过浏览器白名单机制，限制哪些脚本可以执行。

------

## 2. CSRF (Cross-Site Request Forgery) —— 跨站请求伪造

**核心原理：** 攻击者并不直接窃取数据，而是**诱导已登录的用户访问一个恶意链接**，利用浏览器**自动携带 Cookie** 的特性，**冒充用户向服务器发送请求**。

> **比喻：** 攻击者不能直接拿到你的银行钥匙（Cookie），但他趁你没锁门（未退出登录）时，骗你按下了“转账”按钮。

### 攻击条件：

1. 用户已登录受信任网站 A，并在本地留有 Cookie。
2. 用户在**未退出 A 的情况下**，访问了恶意网站 B。

### 防御方案：

- **验证码：** 强制用户进行人机交互，让攻击者无法静默操作。
- **CSRF Token：** 服务器在页面中嵌入一个随机生成的 Token，请求时必须携带该 Token。攻击者可以伪造请求，但无法获取该随机 Token。
- **SameSite Cookie 属性：** 设置 Cookie 的 `SameSite=Strict` 或 `Lax`，限制第三方站点携带 Cookie。
- **验证 Referer / Origin：** 检查请求来源是否为可信域名。

------

## 总结对比

| **特性**         | **XSS (跨站脚本)**             | **CSRF (跨站请求伪造)**             |
| ---------------- | ------------------------------ | ----------------------------------- |
| **主要目标**     | 脚本注入，获取数据/控制权      | 冒用身份，执行非法操作              |
| **是否需要登录** | 不需要（甚至可以针对匿名用户） | **必须**处于登录状态                |
| **信任方向**     | 用户信任网站（网站没过滤好）   | 网站信任用户（浏览器自动发 Cookie） |
| **防御核心**     | 过滤输出、转义、CSP            | Token 验证、SameSite、Referer       |
