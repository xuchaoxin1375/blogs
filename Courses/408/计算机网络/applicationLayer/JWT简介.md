## abstract

在现代 Web 开发中，**JWT (JSON Web Token)** 是一种非常流行的、用于在各方之间安全传输信息的**开放标准 (RFC 7519)**。它通常被用作**身份验证（Authentication）和信息交换**。

简单来说，JWT 就像是一张“数字通行证”，**服务器验证后签发给你**，你后续的请求带着它，服务器就知道你是谁了。

## 1. JWT 的结构

一个 JWT 实际上是一个**很长的字符串**，通过点号 (`.`) 分隔成三个部分：

### **A. Header (头部)**

包含了令牌的类型（即 **JWT**）和所使用的**签名算法**（如 HS256 或 RS256）。

> header 示例:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### **B. Payload (负载)**

这是存放实际数据的地方（称为 Claims）。通常包含用户 ID、过期时间（exp）、签发时间（iat）等。

> **注意：** 这部分只是经过了 Base64 编码，**并没有加密**。任何人都可以解码查看内容，所以千万**不要在这里存放密码或敏感信息**。

### **C. Signature (签名)**

这是最关键的部分。**服务器**使用 **Header** 中指定的算法，结合一个只有服务器知道的**密钥 (Secret)**，对编码后的 Header 和 Payload 进行哈希运算。

- **作用：** 确保令牌在传输过程中没有被篡改。

------

## 2. JWT 的工作流程

1. **登录：** 用户提交用户名和密码。
2. **签发：** 服务器验证成功后，**生成一个 JWT 并返回给客户端**。
3. **存储：** 客户端（浏览器）将 JWT 存放在 `localStorage` 或 `Cookie` 中。
4. **请求：** 客户端后续发送 API 请求时，将 **JWT** 放入 HTTP Header 的 `Authorization: Bearer <token>` 字段中。
5. **验证：** 服务器收到请求后，通过**密钥验证签名的合法性**。如果合法，则处理请求。

------

## 3. 为什么使用 JWT？（优势）

- **无状态 (Stateless)：** 服务器不需要在**数据库或内存**（如 Session）中存储**会话信息**。这对**分布式架构**或**微服务**非常友好，因为任**何一台服务器只要有密钥，就能验证令牌**。
- **跨域友好：** 由于信息不存储在特定服务器的 Session 中，它天然支持跨域名或跨平台的身份校验。
- **性能较好：** 减少了查询数据库或 Redis 的次数。

------

## 4. 潜在的缺点与挑战

- **一旦签发，难以撤回：** JWT 在**有效期内是始终有效**的。除非引入黑名单机制（配合 Redis），否则很难在令牌过期前强制让某个用户下线。
- **体积较大：** 相比于简单的 Session ID，JWT 包含的信息更多，会略微增加每个 HTTP 请求的数据量。
- **安全性依赖密钥：** 如果服务器的密钥泄露，整个系统的身份认证就会崩溃。

------

## 5. 总结：JWT vs Session

| **特性**     | **Session**                      | **JWT**                |
| ------------ | -------------------------------- | ---------------------- |
| **存储位置** | 服务器内存/数据库                | 客户端                 |
| **可扩展性** | 较难（多台服务器需同步 Session） | 优秀（各服务独立校验） |
| **安全性**   | 配合 Cookie，需防范 CSRF         | 需防范 XSS 和数据泄露  |
