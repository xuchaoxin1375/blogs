**Cloudflare 本质上就是一个规模庞大的分布式反向代理（Reverse Proxy）集群。**

当一个网站启用了 Cloudflare，它的网络架构就会发生根本性的变化。我们可以通过“正向”和“反向”的对比，以及 Cloudflare 的实际工作方式来理解它。

### 1. 为什么叫“反向”代理？

我们可以用一个简单的比喻来区分正向和反向代理：

- **正向代理（Forward Proxy）：** 它是客户端（用户）的代理。
  - 比如你使用 VPN 去访问国外的网站，VPN 帮你隐藏了你的真实身份，目标网站只知道请求来自 VPN 服务器。**它代表的是客户端。**
- **反向代理（Reverse Proxy）：** 它是服务端（网站）的代理。
  - 当用户访问网站时，请求并不会直接到达网站的真实服务器（源站），而是先到达反向代理服务器，由反向代理服务器决定去哪里拿数据并返回给用户。用户甚至不知道源站的真实 IP。**它代表的是服务端。**

客户(访客)可以选择是否使用以及使用什么样的正向代理,其无法确定服务端(网站)是否使用代理.

反之,服务端(网站)可以选择是否使用以及使用什么样的反向代理,但是无法决定用户端是否使用代理.

### 2. 启用 Cloudflare 后的网络流向

在没有使用 Cloudflare 之前，用户的访问路径是直连的：

> **用户** $\rightarrow$ 通过 DNS 解析出网站源站 IP $\rightarrow$ **网站源站服务器**

一旦网站启用了 Cloudflare（将域名的 DNS 解析交给了 Cloudflare 并开启了“小黄云”代理）：

> **用户** $\rightarrow$ DNS 解析出 Cloudflare 的 Anycast IP $\rightarrow$ **Cloudflare 边缘节点（反向代理）** $\rightarrow$ **网站源站服务器**

在这个过程中，Cloudflare 完美的履行了反向代理的职责：

1. **隐藏源站：** 任何人去 `ping` 你的域名，拿到的都是 Cloudflare 的 IP，你的源站真实 IP 被安全地保护在幕后。
2. **迎客与分流：** 用户的请求第一站永远是 Cloudflare 的节点。

### 3. 作为反向代理，Cloudflare 顺便做了哪些事？

既然所有的流量都要先经过 Cloudflare 这层“中间人”，它就可以在这个节点上做非常多高附加值的功能，这也是为什么它这么受欢迎的原因：

- **静态缓存（CDN）：** 既然它是反向代理，当它发现用户请求的是一张图片或 CSS 文件，且这个文件已经缓存过了，它就直接返回给用户，根本不需要去打扰你的源站。
- **安全防护（WAF / DDoS 防御）：** 如果有黑客发动 DDoS 攻击，或者发送恶意的 SQL 注入请求，Cloudflare 作为反向代理在第一线就会把这些恶意流量清洗、拦截掉，网站源站甚至毫无感知。
- **SSL/TLS 证书卸载：** 用户的 HTTPS 加密连接可以只建立到 Cloudflare 节点（也就是所谓的灵活/完全模式），减轻了源站服务器计算加密解密的 CPU 压力。
- **负载均衡：** 如果你的后台有多台服务器，Cloudflare 可以作为反向代理把流量均匀地分发到不同的服务器上。

### 总结

Cloudflare 并不是一个简单的 DNS 解析商，它的核心底层技术就是一个**架构在全球各地的、巨大的反向代理网络**。当你开启它的代理功能时，你就相当于把自己的网站服务器搬到了这个巨大反向代理矩阵的保护伞之后。
