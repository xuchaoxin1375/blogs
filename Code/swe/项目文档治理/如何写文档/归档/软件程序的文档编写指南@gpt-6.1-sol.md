**核心原则：文档应让目标读者不依赖作者，也能判断是否适合、正确使用、排查问题，并接手维护。重点是“完成任务”，不是“写得多”。**

## 应该写哪些内容

下面是**可按项目复杂度裁剪的建议清单**：

| 内容           | 应回答的问题                                                 |
| -------------- | ------------------------------------------------------------ |
| **项目说明**   | 做什么、解决什么问题、适合谁、不适合什么场景、当前是否稳定？ |
| **快速开始**   | 需要什么系统、依赖版本和权限？如何安装、配置、运行？**怎样确认成功？** |
| **使用参考**   | 参数、配置项、环境变量、输入输出分别是什么？说明含义、类型、必填性、默认值及示例 |
| **限制与排障** | 有哪些已知限制和危险操作？常见错误如何判断、查看日志和处理？如何求助？ |
| **开发维护**   | 如何搭建开发环境、测试、构建和发布？模块如何协作？**关键设计为什么这样选择？** |
| **部署运维**   | 如何部署、监控、升级、迁移数据、备份恢复和回滚？生产服务尤其需要故障处理指引 |

例如，**备份脚本**不能只写运行命令，还应说明：备份哪些文件、保存到哪里、是否覆盖旧备份、如何判断成功，以及如何恢复。

## 如何组织

- **简单脚本：一个清楚的`README.md`，配合`--help`通常即可起步。**命令行帮助优先展示常用操作和示例，详细解释放入文档。
- **进阶工具或完整项目：`README.md`负责项目介绍、快速开始和导航，详细内容放入`docs/`等位置。**不要把所有内容都塞进首页；GitHub也将项目用途、入门方式、求助渠道和维护者列为README的典型内容。
- 内容较多时，可参考**Diátaxis文档组织框架**，区分：**教程**（带着学习）、**操作指南**（完成具体任务）、**参考手册**（查询准确细节）、**原理说明**（理解背景与设计）。可以相互链接，但不要混成一篇难以查阅的长文。

## 应达到的质量与规范

| 要求                       | 实践重点                                                     |
| -------------------------- | ------------------------------------------------------------ |
| **必须准确、可复现**       | 示例经过实际验证；交代前提、完整步骤和预期结果。不能运行的片段、不适合生产的示例必须标明。 |
| **必须交代风险与边界**     | 推荐把删除、覆盖、权限提升等风险放在操作之前；示例不得包含真实密钥或敏感数据 |
| **必须保持版本一致**       | 推荐采用**文档即代码（Docs as Code）**：纳入版本控制、随变更评审，并通过自动检查验证链接、格式和示例。 |
| **应该清楚、统一、易查找** | 术语和标题一致；命令、文件名使用代码格式；说明操作主体、前置条件和占位符含义；图片不能成为唯一说明。可参考Google技术文档风格指南。 |
| **应该能支撑故障处理**     | 运维手册写清故障影响、诊断方法、缓解措施和求助路径，并随生产环境变化更新。 |
| **可以采用专门规范**       | HTTP API可使用**OpenAPI规范**描述接口契约；它不能替代入门教程、业务解释和运维手册。 |

**注意区分：Diátaxis是组织框架，风格指南是写作参考，OpenAPI是接口描述规范，不是同一种“标准”。按项目实际需求采用，不要机械套模板。**

## 最应避免什么

- **只有功能介绍，没有可执行步骤与成功判据。**
- **只写成功路径，不写错误、限制和风险。**
- 用代码注释、目录树或截图代替完整说明。
- 同一事实复制到多处，修改后互相矛盾。
- 示例未经验证，或者文档长期落后于程序。

**建议的验收方法：找一个没参与开发的人，仅凭文档尝试完成“安装—运行—验证—排障”；维护者再尝试完成“测试—修改—发布—恢复”。卡住的地方，就是文档应优先补齐的地方。**
