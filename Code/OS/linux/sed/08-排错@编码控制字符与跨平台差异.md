`sed` 的“不工作”通常不是 `sed` 本身坏了，而是下面几类问题之一：

- 输入里有看不见的字符：CR(Carriage Return, 回车)、BOM(Byte Order Mark, 字节顺序标记)、NUL(空字节)、制表符、不间断空格。
- 文件编码不是你以为的 UTF-8：例如 Windows PowerShell 写出的 UTF-16LE(小端 UTF-16)。
- 正则方言不对：把 PCRE(Perl Compatible Regular Expressions, Perl 兼容正则) 的 `\d`、`(?=...)` 用在 POSIX 正则里。
- shell 先把脚本改掉了：双引号展开变量、反引号、反斜杠。
- 平台差异：macOS 的 `-i`、`\n` 替换、`a/i/c` 写法与 GNU 不同。
- 命令本身用错：忘了 `g`、忘了 `-n`、`-i` 和 `-n` 组合、地址范围没匹配上。

这一篇按“先看数据，再看正则，再看平台”的顺序排查。

## 先看输入，不要先改正则

匹配不上时，第一步不是反复改正则，而是确认 `sed` 实际看到的字节是什么。

### 查看不可见字符

```shell
$ printf 'a\r\nb\n' | cat -A
a^M$
b$
$ printf 'a\tb\n' | sed -n 'l'
a\tb$
```

- `cat -A` 把行尾显示成 `$`，把 CR 显示成 `^M`，把制表符显示成 `^I`。
- `sed -n 'l'` 用转义形式显示模式空间，行尾同样用 `$` 标记。

两者都能暴露“看起来是空格、实际是别的东西”的字符。

### 查看字节

```shell
$ printf 'a\0b\0' | od -c
0000000   a  \0   b  \0
0000004
$ printf '\xEF\xBB\xBFhello\n' | sed -n 'l'
\357\273\277hello$
```

- `\0` 是 NUL 字节，常见于 UTF-16LE 文件。
- `\357\273\277` 是 UTF-8 BOM 的三个字节，显示在行首。

`hexdump -C` 也能看十六进制，适合定位 BOM、CRLF 和异常字节。

### 判断文件编码

在 Linux/macOS 上：

```bash
file /path/to/data.txt
```

输出可能提示 `UTF-8 Unicode text`、`UTF-16LE`、`with CRLF line terminators` 等。`file` 不是万能的，但能快速排除明显的编码问题。

## 案例：PowerShell 生成的文件为什么匹配不上

旧笔记里有一个真实案例：在 Windows 上用 PowerShell 生成时间戳文件，复制到 Linux 后用 `grep`、`sed` 匹配不到。`cat` 看起来像普通文本，`cat -A` 却显示每个字符之间夹着 `^@`：

```shell
$ cat -A data.txt
M-^?M-~L^@8^@2^@6^@3^@...
```

`^@` 是 NUL 字节，说明文件不是 UTF-8，而是 **UTF-16LE**（Windows PowerShell 5.1 的 `>`、`Out-File` 默认编码）。`sed` 按字节找 `L826...`，看到的却是 `L\0 8\0 2\0 6\0...`，自然匹配不到。

### 不要用 cat 重定向“清洗”

在 Windows PowerShell 5.1 里：

```powershell
cat file > washed.txt
```

`cat` 是 `Get-Content` 的别名，`>` 默认仍然写 UTF-16LE，可能把问题原样带过去。正确目标是写成 **UTF-8 无 BOM**。

### 写入 UTF-8 无 BOM

PowerShell 7（pwsh）：

```powershell
Set-Content -LiteralPath /path/to/data.txt -Value $text -Encoding utf8NoBOM
```

Windows PowerShell 5.1 没有 `utf8NoBOM`，用 .NET 方法：

```powershell
$utf8 = [System.Text.UTF8Encoding]::new($false)
[System.IO.File]::WriteAllText('/path/to/data.txt', $text, $utf8)
```

写完后在 Linux/Git Bash 里核对：

```bash
file /path/to/data.txt
sed -n '1l' /path/to/data.txt
```

### 转换已有文件

在 Linux/macOS 上可以用 `iconv`：

```bash
iconv -f UTF-16LE -t UTF-8 data.txt > data.utf8.txt
```

如果输出开头还有 BOM，再去掉：

```bash
sed '1s/^\xEF\xBB\xBF//' data.utf8.txt > data.clean.txt
```

`tr -d '\0'` 能快速删除 NUL，但它只对“ASCII 范围内的 UTF-16LE”安全；文件里有中文、emoji 等非 ASCII 字符时，直接删 NUL 会破坏内容。能转换编码时优先转换，不要用删除字节的办法糊弄。

## CRLF 与 BOM

### CRLF

Windows 文本常用 `\r\n` 结尾，这一对字符叫 **CRLF**(Carriage Return + Line Feed, 回车换行)。Linux 上的 `sed` 会把 `\r` 当成行内容的一部分，于是：

```shell
$ printf 'a\r\n' | cat -A
a^M$
$ printf 'a\r\n' | sed -n 'l'
a\r$
```

`^M$` 和 `\r$` 都表示行尾多了一个 CR。它会导致：

- `sed 's/foo$/bar/'` 匹配不到，因为 `$` 前面还有一个 `\r`。
- 用 `^`、`$` 锚定的整行匹配失败。
- 输出的文本在终端里看起来正常，但比较或解析时多一个字符。

在 Linux 上删除 CR：

```bash
sed -i.bak 's/\r$//' file.txt
```

在 macOS/BSD 上，`sed` 对 `\r` 的支持不一致，用 `tr` 更稳：

```bash
tr -d '\r' < file.txt > file.unix.txt
```

`dos2unix file.txt` 也是常用选择，前提是系统安装了它。

在 Windows 的 Git Bash/MSYS 中，`sed` 可能默认按文本模式打开文件，自动把 CRLF 转成 LF；这时 `s/\r$//` 看起来“没效果”。要看原始字节，加 `-b`：

```shell
$ printf 'a\r\n' > crlf.txt
$ sed -n 'l' crlf.txt
a$
$ sed -b -n 'l' crlf.txt
a\r$
```

这是平台相关的行为，不是 `sed` 坏了。

### BOM

UTF-8 BOM 是文件开头的三个字节 `EF BB BF`，全称 **字节顺序标记**(Byte Order Mark, BOM)。`sed -n 'l'` 会显示成 `\357\273\277`。它会让 `^#`、`^include` 这类行首锚点匹配失败，因为第一个字符实际是 BOM，不是 `#`。

GNU sed 删除 BOM：

```bash
sed -i.bak '1s/^\xEF\xBB\xBF//' file.txt
```

`\xHH` 是 GNU 扩展；BSD/macOS sed 不一定支持。跨平台时用 `perl` 按字节序列删除：

```bash
perl -i.bak -pe 's/^\xEF\xBB\xBF//' file.txt
```

或者用 `iconv`/编辑器另存为“UTF-8 无 BOM”。

## locale 与多字节字符

`sed` 的字符类、`.`、大小写转换都受 **区域设置**(locale) 影响。行为在不同机器上不一致时，先看：

```bash
locale
```

如果希望按字节、按 ASCII 规则稳定处理，可以临时设置：

```bash
LC_ALL=C sed -n '/^[a-z]*$/p' file.txt
```

但 `LC_ALL=C` 会让中文等多字节字符按字节处理，`[[:alpha:]]` 不再匹配中文。需要处理 UTF-8 文本时，保持 UTF-8 locale，并注意：

- 无效的多字节序列可能让 `.`、`[[:alpha:]]` 的行为变得难以预测。
- GNU 的 `z` 命令清空模式空间时，比 `s/.*//` 更能处理无效多字节序列。
- 大小写转换 `\U`、`\L` 只对 GNU sed 有效，且受 locale 影响。

排查时先用一个最小样本复现：

```bash
printf '中文abc\n' | LC_ALL=C sed -n 'l'
printf '中文abc\n' | sed -n 'l'
```

对比两边输出的字节，就能判断问题是否来自 locale。

## 正则方言问题

下面这些写法在 PCRE（Python、JavaScript、`grep -P`）里常见，在 `sed` 的 POSIX 正则里通常不支持：

| 写法 | 在 sed 中的替代 |
| --- | --- |
| `\d` | `[0-9]` 或 `[[:digit:]]` |
| `\s` | `[[:space:]]`（GNU 支持 `\s`，但不可移植） |
| `\w` | `[[:alnum:]_]`（GNU 支持 `\w`，但不可移植） |
| `(?=...)`、`(?<=...)` | 不支持前瞻/后顾，改用两步处理 |
| `(?:...)` | 不支持非捕获分组 |
| `*?`、`+?` | 不支持懒惰量词，用排除型字符类 |
| `a+`（BRE） | 写成 `a\+`，或加 `-E` |
| <code>a&#124;b</code>（BRE） | 写成 <code>a\&#124;b</code>，或加 `-E` |

确认方言的最快方法是用 `-E` 重写一遍：

```shell
$ echo 'a1' | sed 's/[[:digit:]]/X/'
aX
$ echo 'a1' | sed -E 's/[0-9]+/X/'
aX
```

如果 `-E` 版本能工作，而原命令不能，问题多半在 BRE 的转义上。

## shell 引号问题

同一个脚本，单引号和双引号可能传给 `sed` 不同的内容。

```shell
$ name=world
$ echo hello | sed 's/hello/$name/'
$name
$ echo hello | sed "s/hello/$name/"
world
```

双引号里 `$` 会被 shell 展开；单引号里不会。除此之外：

- 双引号里的反引号会触发命令替换。
- 交互式 bash 里 `!` 可能触发历史展开，脚本里通常不会。
- 反斜杠在双引号里可能被 shell 处理，导致 `\1`、`\n` 层数变化。

排查方法：把脚本单独打印出来，确认 shell 实际传了什么。

```bash
script='s/foo/bar/'
printf '%s\n' "$script"
```

或者临时加 `set -x`，看执行的命令行。

## -i 相关的坑

### macOS 要求 -i 带参数

```shell
# macOS：不备份也要写空字符串
sed -i '' 's/old/new/' file.txt

# Linux/GNU：可以不带参数
sed -i 's/old/new/' file.txt
```

在 macOS 上写 `sed -i 's/old/new/' file.txt`，`-i` 会把 `s/old/new/` 当成备份后缀，真正的脚本位置错位，通常报 `invalid command code` 之类的错误。

可移植的“不备份”写法：

```bash
sed -i.bak 's/old/new/' file.txt && rm file.txt.bak
```

GNU 和 BSD 都接受 `-i.bak`，处理后删掉备份即可。

### -i 后面紧跟选项字母

```shell
# GNU：-E 和 -i 分开，不备份
sed -Ei 's/foo/bar/' file

# GNU：等价于 --in-place=E，生成 fileE 备份
sed -iE 's/foo/bar/' file
```

`-i` 的参数是可选的，所以它会把紧跟的 `E` 吃掉。把 `-i` 放在最后，或显式写 `-i.bak`。

### -i 与 -n 组合导致文件变空

```shell
$ printf 'foo\n' > danger.txt
$ sed -ni 's/foo/bar/' danger.txt
$ wc -c < danger.txt
0
```

`-n` 禁止自动打印，脚本里又没有 `p`，写回文件的内容为空。删掉 `-n`，或确保每一行都有明确的输出。

## GNU 与 BSD/macOS 的主要差异

macOS 自带的是 BSD 系 `sed`。下面这些差异会直接影响脚本能否运行：

| 特性 | GNU sed | BSD/macOS sed |
| --- | --- | --- |
| `-i` 参数 | 可选 | 必需；不备份写 `-i ''` |
| `-i` 备份后缀里的 `*` | 支持，可加前缀或指定目录 | 不支持 |
| `-E` | 支持 | 支持 |
| `-r` | 支持 | 通常支持，等价于 `-E` |
| 替换里的 `\n` | 支持 | 通常不支持；用反斜杠加真实换行 |
| `a`/`i`/`c` 单行写法 | 支持（GNU 扩展） | 不支持；用 `a\` 加换行 |
| `\s`、`\w`、`\S`、`\W` | 支持 | 通常不支持；用 POSIX 字符类 |
| `first~step` 地址 | 支持 | 不支持 |
| `addr,~N` 地址 | 支持 | 不支持 |
| `0,/regex/` | 支持 | 不支持 |
| `Q`、`T`、`R`、`W`、`z`、`e`、`F`、`v` | 支持 | 不支持 |
| `\L`、`\U`、`\l`、`\u`、`\E` | 支持 | 不支持 |
| `-s`、`-z`、`--debug`、`--sandbox` | 支持 | 不支持 |
| `-l` | 设置 `l` 的换行长度 | 行缓冲（含义不同） |
| `-b` | 二进制模式（Windows/Cygwin 有效） | 无 |
| `I` 标志 | 支持 | FreeBSD/macOS 支持，老 BSD 不一定 |
| `-H` 增强正则 | 无 | macOS 支持 |
| `-a` 延迟打开 `w` 文件 | 无 | macOS 支持 |
| `-I` 就地编辑且不重置行号 | 无 | macOS 支持 |

这张表只列常见项。写跨平台脚本时，最稳的策略是：

- 用 `-E`，不用 `-r`。
- 用 `[[:space:]]`、`[[:digit:]]`，不用 `\s`、`\d`。
- 需要换行时用反斜杠加真实换行，不用 `\n`。
- `a`/`i`/`c` 用多行写法。
- `-i` 用 `-i.bak` 加删除备份的方式，或按平台分支。
- 不依赖 `Q`、`T`、`R`、`W`、`z`、`e` 等 GNU 命令。

### 可移植的写法对照

```bash
# GNU：替换里用 \n
sed 's/,/\n/' file

# 可移植：反斜杠加真实换行
sed 's/,/\
/' file
```

```bash
# GNU：单行插入
sed '/pattern/i new line' file

# 可移植：i\ 加换行
sed '/pattern/i\
new line' file
```

```bash
# GNU：不备份就地编辑
sed -i 's/old/new/' file

# 可移植：带备份再删除
sed -i.bak 's/old/new/' file && rm file.bak
```

## 在 macOS 上安装 GNU sed

如果经常在 Linux 和 macOS 之间切换，可以安装 GNU sed：

```bash
brew install gnu-sed
```

安装后的命令名通常是 `gsed`，不是 `sed`。可以先验证：

```bash
gsed --version
```

交互式使用时可以设别名：

```bash
alias sed='gsed'
```

但不要把这条别名写进需要分发的脚本：脚本里的 `sed` 可能仍然指向系统版本，导致“我这里能跑、别人那里报错”。脚本里要么显式调用 `gsed`，要么按平台检测：

```bash
if command -v gsed >/dev/null 2>&1; then
  SED=gsed
else
  SED=sed
fi
```

## 排查清单

按顺序过一遍，大多数问题都能定位：

- 输入是否为空？先用 `printf` 造一个最小样本，排除文件问题。
- 是否忘了 `-n`，或 `p` 和自动打印叠加导致重复？
- 地址是否匹配？先用 `sed -n '/pattern/p'` 单独验证。
- 是否只替换了第一个匹配？检查有没有 `g`。
- 是否有 CR、BOM、NUL、制表符？用 `cat -A`、`sed -n 'l'`、`od -c` 看。
- 文件编码是否是 UTF-8？用 `file`、`iconv` 确认。
- 正则方言是否正确？BRE 的 `\+`、`\|` 是否漏了反斜杠？是否需要 `-E`？
- shell 是否改了脚本？用单引号或打印实际参数确认。
- 是否在 macOS 上？`-i`、`\n`、`a/i/c` 是否需要改写？
- `-i` 是否和 `-n` 组合？文件是否被清空？
- 退出状态和标准错误是什么？不要只看屏幕输出。

### 症状对照

| 症状 | 常见原因 | 处理 |
| --- | --- | --- |
| 完全没有输出 | `-n` 后没有 `p`；输入为空；文件路径错 | 去掉 `-n` 试一次；检查文件 |
| 输出重复 | 没有 `-n` 却用了 `p` | 加 `-n`，或去掉 `p` |
| 匹配不到 | CR/BOM/NUL；正则方言；锚点；locale | 先看字节，再用最小样本 |
| 只改了第一处 | 忘了 `g` | 加 `g` |
| 文件变空 | `-i` 与 `-n` 组合；通配符匹配错 | 从备份恢复；检查脚本 |
| macOS 报 `invalid command code` | `-i` 没带参数；`a/i/c` 写法不对 | 用 `sed -i ''`；改多行写法 |
| 替换后多出空行 | `s/.*//` 清空模式空间，自动打印仍输出空行 | 用 `d` 删除行 |
| `sed: can't read s/...` | 用了 `-e`，后面的内联脚本被当成文件 | 每段脚本都加 `-e` |
| 中文乱码 | 文件编码与终端/locale 不一致 | 用 `file`、`iconv` 检查 |

## 自测

- `cat -A` 显示行尾 `^M$`，说明有什么字符？怎么去掉？
- 文件开头有 `\357\273\277`，会影响什么？GNU sed 怎么去掉？
- 为什么 `sed 's/foo$/bar/'` 在 CRLF 文件上匹配不到？
- macOS 上 `sed -i 's/a/b/' file` 为什么报错？
- `\d` 在 sed 里不工作，应该换成什么？
- `sed -ni 's/a/b/' file` 为什么危险？

参考答案：

- 行尾有 CR；Linux 上用 `sed 's/\r$//'`，macOS 可用 `tr -d '\r'`。
- 是 UTF-8 BOM，会让 `^` 锚定的行首匹配失败；GNU 可用 `sed '1s/^\xEF\xBB\xBF//'`。
- `$` 前面还有一个 `\r`，`foo$` 要求 `o` 后面直接是行尾。
- BSD sed 的 `-i` 需要参数；`s/a/b/` 被当成备份后缀，脚本位置错位。写成 `sed -i '' 's/a/b/' file`。
- 用 `[0-9]` 或 `[[:digit:]]`。
- `-n` 禁止自动打印，又没有 `p`，写回文件的内容为空，原文件会被截断。
