下面给出一套以 **Linux 为主、面向“快速定位磁盘占用并安全清理空间”** 的系统教程。

我建议不要把“磁盘分析”简单理解为“学会 `du`”。更准确的思路是：

> **先确定哪个文件系统有问题，再确定哪个目录增长，再确定具体文件或资源类型，最后使用对应系统的清理机制。**

这套方法既适合个人 Linux 桌面，也适合服务器、开发机、Docker 主机和日常运维。

## 先建立正确的磁盘占用模型

Linux 中谈“磁盘占用”，实际上可能在讨论完全不同的问题。

| 问题                 | 真正要分析的对象         | 常用工具             |
| -------------------- | ------------------------ | -------------------- |
| 哪块盘快满了         | 文件系统容量             | `df`、`duf`          |
| 哪个目录最大         | 目录树累计占用           | `du`、`dust`         |
| 想交互式逐层查看     | 目录树                   | `ncdu`、`gdu`、`dua` |
| 哪些文件特别大       | 单文件                   | `find`               |
| 小文件太多           | inode                    | `df -i`              |
| 删除文件后空间没回来 | 打开的已删除文件         | `lsof`               |
| Docker 占空间        | 镜像、容器、卷、构建缓存 | `docker system df`   |
| Btrfs 空间异常       | extents、快照、共享空间  | `btrfs filesystem`   |
| 系统日志太大         | systemd journal          | `journalctl`         |

因此，第一条重要原则是：

> **不要看到磁盘满了，就直接执行 `du -ah /`。**

因为你甚至还没有确定：

- 是 `/` 满了；
- 还是 `/home` 满了；
- 还是 `/var` 单独挂载的文件系统满了；
- 还是 inode 满了；
- 或者是 Docker、Btrfs 快照、已删除文件造成的特殊占用。

正确的分析过程应该是：

```mermaid
flowchart TD
    A["发现磁盘空间异常"] --> B["检查文件系统容量"]
    B --> C{"块空间满了吗"}
    C -->|"是"| D["定位目标挂载点"]
    C -->|"否"| E["检查 inode"]
    E --> F{"inode 是否耗尽"}
    F -->|"是"| G["寻找海量小文件目录"]
    F -->|"否"| H["检查特殊占用"]

    D --> I["分析一级目录"]
    I --> J["进入最大的目录"]
    J --> K["继续逐层缩小范围"]
    K --> L["定位文件或资源类型"]

    H --> M["已删除但仍打开的文件"]
    H --> N["容器数据"]
    H --> O["快照与 CoW 数据"]
    H --> P["日志或特殊文件系统"]

    L --> Q["确认用途"]
    M --> Q
    N --> Q
    O --> Q
    P --> Q

    Q --> R["使用对应机制安全清理"]
```

## `df` 和 `du` 到底有什么区别

这是理解 Linux 磁盘占用最重要的知识之一。

简单来说：

- `df` 问的是：**文件系统认为用了多少空间？**
- `du` 问的是：**从这个目录树遍历下来，文件占了多少空间？**

GNU Coreutils 将 `df` 定义为报告文件系统空间使用情况，而 `du` 会递归汇总文件或目录的设备占用。 ([man7.org](https://man7.org/linux/man-pages/man1/df.1.html?utm_source=chatgpt.com))

可以想象为：

```mermaid
flowchart LR
    FS["文件系统<br>Filesystem"] --> DF["df<br>读取文件系统空间统计"]

    DIR["目录树<br>Directory Tree"] --> DU["du<br>递归遍历目录和文件"]

    DF --> A["Used / Available"]
    DU --> B["目录累计占用"]
```

例如：

```bash
df -h /
```

得到：

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p2  200G  180G   10G  95% /
```

这里告诉你：

> 根文件系统 `/` 已经使用 180 GB。

但是它没有告诉你：

> 这 180 GB 到底在哪里。

于是继续：

```bash
sudo du -xhd1 /
```

可能看到：

```text
8.0G    /usr
95G     /var
42G     /home
2.1G    /opt
148G    /
```

现在就知道应该调查：

```text
/var
```

然后：

```bash
sudo du -xhd1 /var
```

继续逐层缩小。

这就是最经典的：

> **文件系统定位 -> 目录定位 -> 文件定位**

分析模型。

## 理解逻辑大小与实际磁盘占用

分析磁盘时还有两个很容易混淆的概念。

### Apparent Size

表观大小、逻辑大小（Apparent Size / Logical Size）。

可以粗略理解为：

> 一个程序读取这个文件时，认为这个文件有多大。

例如：

```bash
ls -lh file.img
```

显示：

```text
100G file.img
```

逻辑大小是：

```text
100 GB
```

### Disk Usage

实际磁盘占用、设备占用（Disk Usage / Physical Usage）。

表示：

> 文件系统实际上给这个文件分配了多少存储空间。

GNU `du` 默认报告设备使用量；`--apparent-size` 则报告表观大小。官方文档特别指出，稀疏文件（Sparse File）等情况可能造成两者明显不同。 ([man7.org](https://man7.org/linux/man-pages/man1/du.1.html?utm_source=chatgpt.com))

例如：

```bash
truncate -s 100G test.img
```

查看：

```bash
ls -lh test.img
```

可能显示：

```text
100G test.img
```

但是：

```bash
du -h test.img
```

可能显示：

```text
0 test.img
```

再看：

```bash
du -h --apparent-size test.img
```

可能显示：

```text
100G test.img
```

原因是 `truncate` 可以创建一个 **稀疏文件（Sparse File）**。

逻辑上：

```text
文件长度 = 100 GB
```

物理上：

```text
实际分配数据块 ≈ 0
```

可以理解为：

```mermaid
flowchart TD
    A["逻辑文件 100 GB"] --> B["0 - 1 GB<br>实际数据"]
    A --> C["1 - 99 GB<br>Hole"]
    A --> D["99 - 100 GB<br>实际数据"]

    C --> E["没有真正分配对应数据块"]
```

因此：

```bash
ls -lh
```

和：

```bash
du -h
```

回答的是不同问题。

### 实用判断

想知道：

> 删除这个文件大概能释放多少实际磁盘空间？

优先看：

```bash
du -h FILE
```

想知道：

> 应用程序看到的文件长度是多少？

可以看：

```bash
ls -lh FILE
```

或：

```bash
du --apparent-size -h FILE
```

现代工具 `dust` 也明确区分实际占用和 apparent size，并提供 `-s` 查看后者。 ([GitHub](https://github.com/bootandy/dust))

## 磁盘分析工具地图

目前比较实用的一组工具如下。

| 工具        | 定位         | 主要优势              | 推荐场景      |
| ----------- | ------------ | --------------------- | ------------- |
| `df`        | 文件系统容量 | 标准、普遍存在        | 第一轮检查    |
| `duf`       | 现代 `df`    | 输出清晰、排序、inode | 快速看磁盘    |
| `du`        | 目录占用     | 标准、脚本友好        | 通用分析      |
| `dust`      | 现代 `du`    | 自动突出大目录        | 快速定位      |
| `ncdu`      | TUI 分析器   | 稳定、简单、远程友好  | SSH 服务器    |
| `gdu`       | 高性能 TUI   | 并行扫描              | SSD、大目录树 |
| `dua`       | 高性能分析器 | 默认并行、交互模式    | SSD、开发机   |
| `erdtree`   | 文件系统分析 | 多线程、树形、元数据  | 开发目录      |
| `diskonaut` | Treemap TUI  | 可视化面积图          | 视觉分析      |
| `find`      | 文件筛选     | 条件能力极强          | 查大文件      |
| `fd`        | 现代文件搜索 | 并行遍历、语法友好    | 日常文件搜索  |

其中，`dua` 默认进行并行扫描，项目明确将充分利用 SSD；`gdu` 同样主要针对 SSD 的并行扫描优化，HDD 也可使用，但性能收益通常没有 SSD 明显。 ([GitHub](https://github.com/byron/dua-cli))

### 我的实际推荐

普通 Linux 用户：

```text
duf + dust + ncdu
```

服务器：

```text
df + du + ncdu
```

NVMe / SSD 开发机：

```text
duf + dust + gdu
```

超大代码目录：

```text
erdtree + gdu
```

Docker 主机：

```text
duf + gdu + docker system df
```

如果只能安装一个额外工具：

> **安装 `ncdu`。**

如果想要最快地“一眼看到大户”：

> **使用 `dust`。**

如果 SSD 中有数百万文件，需要尽量快地扫描：

> **考虑 `gdu` 或 `dua`。**

## 先用 `df` 找到出问题的文件系统

最基本的命令：

```bash
df -h
```

推荐：

```bash
df -hT
```

其中：

- `-h`：Human-readable，人类可读单位；
- `-T`：显示文件系统类型。

例如：

```text
Filesystem     Type   Size  Used Avail Use% Mounted on
/dev/nvme0n1p2 ext4   100G   92G  3.0G  97% /
/dev/nvme0n1p3 ext4   500G  180G  295G  38% /home
tmpfs          tmpfs   16G   20M   16G   1% /run
```

这里不要看到：

```text
/home 180G
```

就认为 `/home` 有问题。

真正应该优先关注：

```text
Use%
Avail
```

上例中：

```text
/       97%
/home   38%
```

因此问题是根文件系统 `/`。

`df` 官方定义就是报告文件所在文件系统的空间情况；不给参数时会显示当前挂载文件系统的统计。 ([man7.org](https://man7.org/linux/man-pages/man1/df.1.html?utm_source=chatgpt.com))

### 指定路径查询

非常实用：

```bash
df -h /var/lib/docker
```

或者：

```bash
df -h ~/Downloads
```

它回答的是：

> 这个路径位于哪个文件系统，这个文件系统还有多少空间？

例如：

```bash
df -h /var/lib/docker
```

比：

```bash
df -h
```

然后人工找挂载点更方便。

## 使用 `duf` 替代日常 `df`

`duf` 的定位非常明确：

> Disk Usage/Free Utility，现代化 `df` 替代工具。

项目支持按 size、used、available、usage、inode 等字段排序，也能够直接显示 inode 信息和 JSON 输出。 ([GitHub](https://github.com/muesli/duf))

直接运行：

```bash
duf
```

通常比：

```bash
df -hT
```

更加直观。

按使用率排序：

```bash
duf --sort usage
```

只显示关注字段：

```bash
duf --output mountpoint,size,used,avail,usage
```

查看 inode：

```bash
duf --inodes
```

自动化处理：

```bash
duf --json
```

### `duf` 不是什么

特别注意：

> `duf` 不是目录分析工具。

它回答：

```text
哪个文件系统满了？
```

不回答：

```text
/var 里面哪个目录最大？
```

所以经典组合是：

```text
duf
  |
  +-- 发现 / 快满
        |
        +-- dust /
             或
        +-- ncdu /
```

## 使用 `du` 逐层定位大目录

这是 Linux 上最应该掌握的方法。

### 查看当前目录总大小

```bash
du -sh .
```

解释：

- `-s`：summarize，只显示汇总；
- `-h`：human-readable。

例如：

```text
53G     .
```

### 查看指定目录

```bash
du -sh /var
```

### 查看一级子目录

```bash
du -h --max-depth=1 /var
```

GNU Coreutils 也支持短选项：

```bash
du -hd1 /var
```

GNU `du` 的 `--max-depth=N` 只显示距离起始参数不超过 N 层的汇总；`--max-depth=0` 等价于汇总模式。 ([man7.org](https://man7.org/linux/man-pages/man1/du.1.html?utm_source=chatgpt.com))

输出：

```text
1.2G    /var/cache
18G     /var/lib
5.4G    /var/log
200M    /var/tmp
25G     /var
```

现在知道：

```text
/var/lib
```

最大。

继续：

```bash
du -hd1 /var/lib
```

这就是所谓的：

> **逐层钻取（Drill Down）**

## 分析根目录时强烈建议使用 `-x`

经典命令：

```bash
sudo du -xhd1 /
```

这里最重要的是：

```text
-x
```

也就是：

```text
--one-file-system
```

含义：

> 不跨越文件系统边界。

GNU `du` 和 `ncdu` 都提供 one-file-system 语义；`ncdu -x` 明确表示扫描时不跨文件系统。 ([man7.org](https://man7.org/linux/man-pages/man1/du.1.html?utm_source=chatgpt.com))

假设：

```text
/
├── home
│   └── 实际挂载 /dev/nvme0n1p3
├── mnt
│   └── NAS
└── var
```

如果运行：

```bash
sudo du -hd1 /
```

可能连：

```text
/home
/mnt/nas
```

一起扫描。

结果可能是：

```text
8 TB /
```

但根文件系统实际上只有：

```text
100 GB
```

这是因为 `du` 穿过了挂载点。

所以调查：

```text
根文件系统为什么满
```

推荐：

```bash
sudo du -xhd1 /
```

其思想是：

```text
df 发现哪个文件系统满
             |
             v
du -x 只调查这个文件系统
```

这是非常重要的最佳实践。

## 推荐的 `du` 大目录定位命令

查看根目录一级占用：

```bash
sudo du -xhd1 / 2>/dev/null
```

排序：

```bash
sudo du -xhd1 / 2>/dev/null | sort -h
```

最大的显示在最后。

例如：

```text
4.0K    /mnt
16M     /etc
5.1G    /opt
12G     /usr
71G     /var
90G     /
```

进入 `/var`：

```bash
sudo du -xhd1 /var 2>/dev/null | sort -h
```

假设：

```text
500M    /var/cache
4.2G    /var/log
61G     /var/lib
66G     /var
```

继续：

```bash
sudo du -xhd1 /var/lib 2>/dev/null | sort -h
```

可能出现：

```text
2.4G    /var/lib/snapd
8.0G    /var/lib/flatpak
43G     /var/lib/docker
54G     /var/lib
```

那么问题已经基本定位：

```text
Docker
```

整个过程可能只有三条命令。

## 为什么不推荐一上来 `du -ah /`

很多教程喜欢：

```bash
du -ah / | sort -h
```

我不推荐把它当成第一步。

原因有几个。

### 输出量巨大

`-a` 表示显示所有文件。

如果系统有：

```text
3,000,000 个文件
```

就可能产生数百万行输出。

### 排序需要处理全部数据

```bash
sort
```

需要接收整个结果集。

### 容易跨挂载点

如果没有：

```text
-x
```

可能扫描：

- NAS；
- NFS；
- USB 磁盘；
- Docker mount；
- 其他文件系统。

### 信息密度低

真正的问题可能只是：

```text
/var/lib/docker
```

却遍历了整个系统。

正确方法是：

```text
df
 |
 v
du depth=1
 |
 v
最大目录
 |
 v
继续 depth=1
```

复杂度从“全盘找针”变成“二分式缩小范围”。

## `dust`：我最推荐的现代 `du`

`dust` 是 Rust 编写的现代目录占用分析工具，其设计目标就是：

> 不需要手工组合 `du + sort + head`，快速显示目录树中最大的空间消费者。

官方 README 表示，它会根据终端高度显示较大的目录或文件，并智能地向大目录递归。 ([GitHub](https://github.com/bootandy/dust))

直接：

```bash
dust
```

分析目录：

```bash
dust /var
```

限制显示数量：

```bash
dust -n 20 /var
```

查看 50 个主要空间消费者：

```bash
dust -n 50 /
```

限制目录深度：

```bash
dust -d 3 /var
```

只看目录：

```bash
dust -D /var
```

显示完整路径：

```bash
dust -p /var
```

### 为什么 `dust` 很适合新手

传统操作：

```bash
du -h --max-depth=2 /var | sort -h
```

使用 `dust`：

```bash
dust /var
```

核心价值不只是“命令短”。

而是它在做：

```mermaid
flowchart LR
    A["扫描目录"] --> B["计算占用"]
    B --> C["识别大目录"]
    C --> D["选择性向大目录递归"]
    D --> E["树形展示"]
```

因此你更容易看到：

```text
/var
 ├─ lib
 │   └─ docker
 │       └─ overlay2
 └─ log
     └─ journal
```

而不是得到一大堆平铺行。

### 一个推荐习惯

发现根文件系统满：

```bash
dust -n 30 /
```

发现 `/var` 可疑：

```bash
dust -n 30 /var
```

发现 Docker：

```bash
dust -n 30 /var/lib/docker
```

不过，一旦确认是 Docker：

> 不建议继续手工删除 `/var/lib/docker` 下的文件。

应该切换到：

```bash
docker system df
```

后面会详细解释。

## `ncdu`：服务器上的经典选择

`ncdu` 的全称来自：

> NCurses Disk Usage

它是文本用户界面（Text User Interface，TUI）磁盘分析器，项目定位就是在没有完整图形桌面的远程服务器上寻找空间大户。 ([Yorhel](https://dev.yorhel.nl/ncdu?utm_source=chatgpt.com))

运行：

```bash
ncdu
```

分析根目录：

```bash
sudo ncdu /
```

更推荐：

```bash
sudo ncdu -x /
```

`-x`：

```text
只分析当前文件系统
```

这是服务器上非常经典的命令：

```bash
sudo ncdu -x /
```

然后使用键盘逐层进入目录。

### 为什么 `ncdu` 特别适合 SSH

它不需要：

- X11；
- Wayland；
- Web 服务；
- 浏览器。

只需要终端。

因此：

```text
SSH
 |
 v
ncdu
 |
 v
方向键浏览目录
```

非常自然。

### 排除目录

例如不分析缓存：

```bash
ncdu --exclude '.cache' /home
```

或者使用排除文件：

```bash
ncdu -X exclude.txt /home
```

`ncdu` 官方文档支持 `--exclude` 和 `--exclude-from` 等扫描过滤机制。 ([Yorhel](https://dev.yorhel.nl/ncdu/man?utm_source=chatgpt.com))

### 扫描大型服务器时

推荐：

```bash
sudo ncdu -x /
```

而不是：

```bash
sudo ncdu /
```

否则可能进入：

```text
/mnt/nfs
```

然后开始扫描整个 NAS。

## `gdu`：SSD 上非常实用的高速工具

`gdu` 是 Go 编写的磁盘使用分析器。

项目明确说明：

> 主要面向 SSD，可以充分利用并行处理；HDD 同样可以运行，但性能增益没有 SSD 那么明显。 ([GitHub](https://github.com/dundee/gdu))

```bash

```

```bash

```


尤其适合：

```text

开发工作站

```

例如目录结构：

```text

├── project-b/node_modules
```

可能包含：


在这种情况下，并行目录扫描工具通常比传统串行式目录分析体验更好。

### HDD 上为什么不一定越并行越快

机械硬盘（Hard Disk Drive，HDD）有机械寻道。

假设线程同时请求：

```text
目录 A
目录 Z
目录 B
目录 Y
```

磁头可能不断移动。

抽象来看：

```mermaid
flowchart LR
    A["线程 A"] --> D["HDD"]
    B["线程 B"] --> D
    C["线程 C"] --> D
    E["线程 D"] --> D

    D --> F["大量随机寻道"]
```

SSD 没有机械磁头。

因此大量并行元数据读取更容易获得收益。

所以：

> **现代并行磁盘分析工具的“快”通常与存储介质、目录结构、缓存状态和文件数量有关。**

不能简单理解为：

```text
Rust/Go 工具一定比 du 快十倍
```

## 查找超大文件

目录大不一定意味着：

```text
很多文件
```

有时只是一个文件：

```text
80 GB
```

这时候使用 `find`。

### 查找大于 1 GB 的文件

```bash
sudo find / -xdev -type f -size +1G 2>/dev/null
```

解释：

| 参数          | 含义         |
| ------------- | ------------ |
| `/`           | 从根目录开始 |
| `-xdev`       | 不跨文件系统 |
| `-type f`     | 普通文件     |
| `-size +1G`   | 大于 1 GiB   |
| `2>/dev/null` | 隐藏权限错误 |

GNU `find` 支持 `-size`、`-xdev` 和 `-printf` 等条件与输出机制。 ([man7.org](https://man7.org/linux/man-pages/man1/find.1.html?utm_source=chatgpt.com))

### 显示文件大小

GNU `find`：

```bash
sudo find / -xdev -type f -size +1G \
  -printf '%s\t%p\n' 2>/dev/null
```

输出：

```text
42949672960    /var/lib/libvirt/images/vm.qcow2
18253611008    /home/user/Downloads/archive.tar
8589934592     /var/log/app.log
```

其中：

```text
%s
```

是字节大小。

### 按大小排序

```bash
sudo find / -xdev -type f -size +1G \
  -printf '%s\t%p\n' 2>/dev/null |
sort -nr
```

然后：

```bash
sudo find / -xdev -type f -size +1G \
  -printf '%s\t%p\n' 2>/dev/null |
sort -nr |
head -n 20
```

得到最大的 20 个文件。

### 更稳健地处理奇怪文件名

Linux 文件名理论上可以包含：

```text
空格
Tab
换行
```

所以严谨脚本中，应使用 NUL 分隔。

例如：

```bash
sudo find / -xdev -type f -size +1G \
  -printf '%s\t%p\0' 2>/dev/null |
sort -z -nr |
head -z -n 20 |
tr '\0' '\n'
```

日常人工排查通常没有必要这么复杂。

但是写自动化脚本时要知道：

> **换行不是绝对安全的文件名分隔符，NUL 才是经典安全方案。**

## 使用 `find` 按修改时间找增长文件

有时你的问题不是：

> 哪个文件最大？

而是：

> 为什么今天磁盘突然少了 50 GB？

此时应该考虑：

```text
最近修改的文件
```

例如查看过去 24 小时修改的文件：

```bash
sudo find /var -xdev -type f -mtime -1 2>/dev/null
```

大于 100 MB：

```bash
sudo find /var -xdev \
  -type f \
  -mtime -1 \
  -size +100M \
  -printf '%TY-%Tm-%Td %TH:%TM\t%s\t%p\n' \
  2>/dev/null
```

然后排序：

```bash
sudo find /var -xdev \
  -type f \
  -mtime -1 \
  -size +100M \
  -printf '%s\t%p\n' \
  2>/dev/null |
sort -nr
```

这种方法对于排查：

```text
日志暴涨
数据库 dump
程序 core dump
临时文件
错误循环产生的数据
```

特别有效。

## inode 耗尽：明明有空间却不能创建文件

检查：

```bash
df -i
```

GNU `df` 的 `-i` 或 `--inodes` 会显示 inode 信息，而不是普通块空间统计。 ([man7.org](https://man7.org/linux/man-pages/man1/df.1.html?utm_source=chatgpt.com))

例如：

```text
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/nvme0n1p2  6553600 6553590      10  100% /
```

但是：

```bash
df -h
```

可能显示：

```text
20G available
```

于是出现：

```text
No space left on device
```

很多新手会问：

> 明明还有 20 GB，为什么说没有空间？

原因可能是：

```text
inode 用完
```

### inode 可以粗略理解成什么

可以把 inode 粗略理解为：

> 文件系统用于描述文件对象的元数据记录。

目录里：

```text
a.txt
b.txt
c.txt
```

这些都是文件对象。

即使每个只有：

```text
1 byte
```

也仍然需要相应的文件系统元数据。

所以：

```text
几百万个小文件
```

可能比：

```text
一个 500 GB 文件
```

更容易耗尽 inode。

## 怎么找哪个目录文件数量特别多

简单方法：

```bash

```

查看某目录文件数量：

```bash
find /var/cache -xdev -type f 2>/dev/null | wc -l
```

不过这种方法需要遍历。

针对一级目录，可以写：

```bash
for dir in /var/*; do

done
```

可能得到：

```text

/var/lib        825013
/var/log        322
/var/spool      7854192
```

此时：

```text
/var/spool
```

非常可疑。

继续分析。

常见海量小文件来源包括：

```text

图片缩略图
构建缓存
包管理缓存
临时文件
程序错误循环
```

不要看到几百万文件就立即：

```bash
rm -rf
```

应该先确认：

> 谁创建它们？

## 为什么 `df` 很满，但 `du` 找不到那么多数据

这是 Linux 磁盘排查中非常经典的问题。

例如：

```bash
df -h /
```

显示：

```text
Used: 190G
```

但是：

```bash
sudo du -xsh /
```

显示：

```text
120G
```

相差：

```text
70 GB
```

不要立即认为：

```text
du 坏了
```

可能的原因包括：

- 已删除但仍被进程打开的文件；
- Btrfs / CoW / 快照共享空间；
- 挂载点覆盖；
- 文件系统元数据；
- 保留空间；
- `du` 没有权限读取部分目录；
- 稀疏、压缩或共享 extent 语义；
- 文件系统正在变化。

其中最值得优先检查的是：

> **deleted but open file**

## 文件删了，为什么空间没有释放

Linux 中：

```bash
rm app.log
```

本质上可以理解为：

> 删除目录项对应的名字链接。

如果进程仍持有该文件的打开文件描述符（File Descriptor，FD），文件对象可能仍然存在。

例如：

```text
Java 服务
   |
   +-- fd 7
          |
          +-- app.log
```

执行：

```bash
rm app.log
```

目录中：

```text
app.log 消失
```

但：

```text
Java 服务
   |
   +-- fd 7
          |
          +-- 原文件对象仍然打开
```

于是：

```text
ls 看不到
du 扫不到正常路径
df 仍显示空间被使用
```

`lsof` 的 `+L1` 可以选择仍然打开但已经被 unlink 的文件。 ([man7.org](https://man7.org/linux/man-pages/man8/lsof.8.html?utm_source=chatgpt.com))

检查：

```bash
sudo lsof +L1
```

常见输出类似：

```text
COMMAND   PID USER  FD   TYPE DEVICE SIZE/OFF NLINK NAME
java     1234 app   7w   REG  259,2      50G     0 /var/log/app.log (deleted)
```

关键：

```text
(deleted)
```

和：

```text
SIZE/OFF 50G
```

现在找到那 50 GB 了。

### 怎么释放

最推荐：

> 正常重启对应服务。

例如：

```bash
sudo systemctl restart myapp.service
```

然后确认：

```bash
sudo lsof +L1
```

再检查：

```bash
df -h
```

### 不要第一反应就是 kill -9

推荐顺序：

```text
确认进程
 |
 v
确认文件
 |
 v
判断服务影响
 |
 v
正常 reload / restart
 |
 v
检查空间
```

使用：

```bash
kill -9
```

应该是更靠后的手段。

## 挂载点覆盖也会造成“文件找不到”

假设：

```text
/data
```

原本有：

```text
/data/backup.tar    100 GB
```

后来在 `/data` 上挂载了一块新磁盘：

```bash
mount /dev/sdb1 /data
```

现在：

```bash

```

看到的是：

```text
/dev/sdb1 的内容
```

原来根文件系统中的：

```text
/data/backup.tar
```

被挂载点遮住了。

它不是删除了。

只是：

> 当前路径视图被新的文件系统覆盖。

抽象来看：

```mermaid
flowchart TD
    A["根文件系统"] --> B["/data"]
    B --> C["backup.tar 100 GB"]

    D["挂载 /dev/sdb1 到 /data"] --> E["VFS 路径视图"]
    E --> F["/data 显示 /dev/sdb1 内容"]

    C --> G["原数据仍在底层文件系统"]
    G --> H["但普通 ls /data 看不到"]
```

因此可能出现：

```text
df 说根盘用了很多
du / 看起来数据不够
```

这属于更高级的排查场景。

首先查看挂载：

```bash
findmnt
```

查询路径对应挂载：

```bash
findmnt -T /data
```

也可以：

```bash
df -h /data
```

重点是建立：

> **目录路径和文件系统不是同一个概念。**

目录可以成为：

```text
Mount Point
```

即挂载点。

## 分析 systemd Journal

查看当前 journal 使用量：

```bash
journalctl --disk-usage
```

例如：

```text
Archived and active journals take up 8.0G
```

清理到指定容量：

```bash
sudo journalctl --vacuum-size=1G
```

按照时间：

```bash
sudo journalctl --vacuum-time=7d
```

`journalctl` 官方文档提供 `--vacuum-size`、`--vacuum-time` 和 `--vacuum-files`，用于清理归档 journal；时间和容量限制还可以组合使用。 ([自由桌面](https://www.freedesktop.org/software/systemd/man/journalctl.html?utm_source=chatgpt.com))

```bash
sudo journalctl \
  --vacuum-size=1G \
  --vacuum-time=14d
```

### 最佳实践

紧急清理：

```bash
journalctl --disk-usage
sudo journalctl --vacuum-size=1G
```

长期治理：

> 配置 journald 的容量策略。

而不是每两个月手工清一次。

systemd 的 `journald.conf` 支持文件系统使用限制相关配置；官方文档也说明默认限制会受到文件系统比例和容量上限规则影响。 ([自由桌面](https://www.freedesktop.org/software/systemd/man/journald.conf.html?utm_source=chatgpt.com))


APT：

```bash
sudo apt clean
```

或：

```bash
sudo apt autoclean
```

两者不是完全一样。

APT 官方手册说明：

- `clean` 会清除下载的软件包缓存；
- `autoclean` 只删除已经无法再下载、基本无用的包文件；
- `autoremove` 删除作为依赖自动安装、后来已不再需要的软件包。 ([Debian Manpages](https://manpages.debian.org/trixie/apt/apt-get.8.en.html?utm_source=chatgpt.com))

因此：

```bash
sudo apt clean
```

是：

```text
清包缓存
```

而：

```bash
sudo apt autoremove
```

是：

```text
处理不再需要的自动依赖
```

不要混为一谈。

运行：

```bash
sudo apt autoremove
```

之前应仔细查看待删除列表。APT 官方文档同样提醒用户检查其中是否包含实际上希望保留的软件。 ([Debian Manpages](https://manpages.debian.org/testing/apt/apt.8.en.html?utm_source=chatgpt.com))

### Fedora

查看：

```bash
sudo du -sh /var/cache/dnf
```

清理：

```bash
sudo dnf clean all
```

Fedora 官方文档在系统升级清理流程中也使用 `dnf clean all` 清除 DNF 缓存。 ([docs.fedoraproject.org](https://docs.fedoraproject.org/en-US/quick-docs/upgrading-fedora-online/?utm_source=chatgpt.com))

### Arch Linux

重点：

```text
/var/cache/pacman/pkg
```

查看：

```bash
sudo du -sh /var/cache/pacman/pkg
```

Arch 文档将包缓存明确列为系统维护中的空间清理对象。 ([wiki.archlinux.org](https://wiki.archlinux.org/title/System_maintenance?utm_source=chatgpt.com))

但是 Arch 用户尤其应该注意：

> 软件包缓存有降级价值。

Arch 的降级文档明确提到，如果旧版本仍保留在 pacman 缓存，可以直接用于降级。 ([wiki.archlinux.org](https://wiki.archlinux.org/title/Downgrading_packages?utm_source=chatgpt.com))

因此不推荐无脑：

```text
全部永久删除
```

更合理的是保留有限数量的历史版本。

## Docker 主机不要直接 `rm -rf /var/lib/docker`

假设：

```bash
sudo du -sh /var/lib/docker
```

显示：

```text
180G
```

很多人的第一想法：

```bash
sudo rm -rf /var/lib/docker/*
```

这是危险操作。

因为 Docker 有自己的对象模型：

```mermaid
flowchart TD
    A["Docker Disk Usage"] --> B["Images"]
    A --> C["Containers"]
    A --> D["Local Volumes"]
    A --> E["Build Cache"]

    B --> F["共享 Layer"]
    C --> G["Writable Layer"]
    D --> H["持久化数据"]
    E --> I["BuildKit / 构建缓存"]
```

正确的第一步：

```bash
docker system df
```

Docker 官方将该命令定义为显示 Docker daemon 使用的磁盘空间信息。 ([Docker Documentation](https://docs.docker.com/reference/cli/docker/system/df/?utm_source=chatgpt.com))

详细：

```bash
docker system df -v
```

可能看到：

```text
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          120     10       85GB      70GB
Containers      30      5        12GB      8GB
Local Volumes   50      20       60GB      30GB
Build Cache                       40GB      38GB
```

注意：

```text
RECLAIMABLE
```

这是非常重要的信息。

### 为什么不能只用 `du`

Docker 镜像存在共享 Layer。

例如：

```text
Image A
├── Ubuntu Layer 500 MB
└── App A 100 MB

Image B
├── Ubuntu Layer 500 MB
└── App B 200 MB
```

简单看：

```text
Image A = 600 MB
Image B = 700 MB
```

不能直接得出：

```text
总占用 = 1.3 GB
```

因为：

```text
Ubuntu Layer
```

可能共享。

Docker `system df -v` 会区分共享空间（Shared Size）与镜像独占空间（Unique Size）。 ([Docker Documentation](https://docs.docker.com/reference/cli/docker/system/df/?utm_source=chatgpt.com))

### 清理未使用资源

先查看：

```bash
docker system df -v
```

然后根据情况分别分析。

统一清理：

```bash
docker system prune
```

Docker 官方说明，该命令会删除未使用的数据，包括停止的容器、未使用网络、相关镜像和构建缓存；卷需要特别考虑相应选项。 ([Docker Documentation](https://docs.docker.com/reference/cli/docker/system/prune/?utm_source=chatgpt.com))

更激进：

```bash
docker system prune -a
```

注意：

```text
-a
```

可能删除所有当前未被容器使用的镜像，而不仅仅是 dangling image。

所以生产机器上不要形成：

```text
磁盘满
  |
  v
复制 docker system prune -a --volumes
  |
  v
按 Enter
```

这样的习惯。

尤其：

```text
Volume
```

可能保存：

```text
数据库数据
上传文件
应用状态
```

必须先确认用途。

## Btrfs 上不要完全相信普通 `du` 直觉

如果使用：

```text
Btrfs
```

必须理解：

```text
Copy-on-Write
Snapshot
Reflink
Shared Extent
```

### 什么是 CoW

CoW：

> Copy-on-Write，写时复制。

假设文件：

```text
A
```

使用 reflink 创建：

```text
B
```

开始时：

```mermaid
flowchart TD
    A["File A"] --> E["Extent X"]
    B["File B"] --> E
```

两个文件可以引用共享 extent。

修改 B 的一部分后：

```mermaid
flowchart TD
    A["File A"] --> X["Shared Extent X"]
    B["File B"] --> X
    B --> Y["New Extent Y"]
```

因此：

```text
文件逻辑大小之和
```

不等于：

```text
实际独占磁盘空间
```

Btrfs 官方文档明确说明子卷可以共享文件 extent，snapshot 本身也是 subvolume；reflink 文件在修改前可以共享 extent。 ([BTRFS 文档](https://btrfs.readthedocs.io/en/latest/Subvolumes.html?utm_source=chatgpt.com))

### 使用 Btrfs 自己的空间命令

查看：

```bash
sudo btrfs filesystem usage /
```

更详细地分析文件或目录共享空间：

```bash
sudo btrfs filesystem du /path
```

汇总：

```bash
sudo btrfs filesystem du -s /path
```

`btrfs filesystem du` 会考虑共享 extent，并报告相关 shared-space 统计。 ([BTRFS 文档](https://btrfs.readthedocs.io/en/latest/btrfs-filesystem.html?utm_source=chatgpt.com))

### 为什么删除文件不一定释放预期空间

假设：

```text
原文件 100 GB
快照引用 100 GB extent
```

删除原文件：

```text
原文件引用消失
```

但是：

```text
快照仍引用 extent
```

那么 extent 不能释放。

所以：

```text
rm 100 GB 文件
```

不一定意味着：

```text
df Available +100 GB
```

### 快照不是备份

Btrfs 官方文档特别提醒，快照本身并不会让数据“更安全”；它可以保存在线历史状态，但不能天然替代独立备份。 ([BTRFS 文档](https://btrfs.readthedocs.io/en/latest/Subvolumes.html?utm_source=chatgpt.com))

例如：

```text
SSD 损坏
```

原子卷和同盘快照可能一起损失。

## 符号链接与硬链接也要理解

### Symbolic Link

符号链接（Symbolic Link，Symlink）：

```text
link -> target
```

本身是独立的文件系统对象，保存目标路径。

通常：

```bash
du
```

不会默认递归跟随普通目录中的符号链接目标。

分析工具中经常有：

```text
--follow
-L
```

类似选项。

磁盘审计时：

> 不要随便开启“跟随全部符号链接”。

否则可能：

```text
重复遍历
跨目录
进入意外路径
```

### Hard Link

硬链接（Hard Link）更特殊。

例如：

```bash
ln fileA fileB
```

可能是：

```mermaid
flowchart TD
    A["fileA"] --> I["inode 123"]
    B["fileB"] --> I
    I --> D["Data Blocks"]
```

这里：

```text
fileA
fileB
```

是两个目录项。

但它们引用：

```text
同一个 inode
同一份数据
```

所以简单把：

```text
ls -l fileA 的大小
+
ls -l fileB 的大小
```

相加，可能产生重复理解。

优秀的磁盘占用分析工具通常需要专门处理 hard link。

这也是：

> “看文件逻辑长度”和“分析真正磁盘占用”不同的原因之一。

## 不要把缓存一概视为“垃圾”

Cache：

> 缓存。

缓存的目的通常是：

```text
用磁盘换时间
```

例如：

```text
npm cache
Cargo registry
Gradle cache
pip cache
浏览器 cache
```

删除后可能发生：

```text
重新下载
重新解压
重新构建
```

所以：

```text
可删除
```

不等于：

```text
应该经常删除
```

更好的决策模型：

| 情况           | 建议               |
| -------------- | ------------------ |
| 磁盘紧急告警   | 清理高收益缓存     |
| 缓存明显失控   | 清理并配置限制     |
| 空间充足       | 通常不必处理       |
| CI 临时 runner | 可以积极清理       |
| 离线开发机     | 谨慎清包缓存       |
| 网络很慢       | 缓存可能非常有价值 |

正确的问题应该是：

> **删除 20 GB 缓存，未来付出的重新下载和重新构建成本是否值得？**

## 一套我推荐的现代 Linux 磁盘排查流程

假设报警：

```text
No space left on device
```

### 先看块空间

```bash
df -hT
```

或者：

```bash
duf
```

假设发现：

```text
/ 97%
```

### 再看 inode

```bash
df -i /
```

或者：

```bash
duf --inodes
```

如果 inode 正常，继续。

### 确认路径所属文件系统

```bash
findmnt -T /
```

检查挂载布局：

```bash
findmnt
```

### 一级目录定位

标准方案：

```bash
sudo du -xhd1 / 2>/dev/null | sort -h
```

现代方案：

```bash
sudo dust -n 30 /
```

交互方案：

```bash
sudo ncdu -x /
```

高速 SSD：

```bash
sudo gdu /
```

### 假设发现 `/var` 最大

```bash
sudo du -xhd1 /var 2>/dev/null | sort -h
```

或：

```bash
sudo dust -n 30 /var
```

### 根据类型切换工具

如果是：

```text
/var/log
```

执行：

```bash
journalctl --disk-usage
```

和：

```bash
find /var/log -xdev -type f -size +100M
```

如果是：

```text
/var/lib/docker
```

执行：

```bash
docker system df -v
```

如果是：

```text
Btrfs
```

执行：

```bash
btrfs filesystem usage /
btrfs filesystem du -s /path
```

如果普通目录仍找不到占用：

```bash
sudo lsof +L1
```

### 最后才执行删除

推荐：

```mermaid
flowchart LR
    A["观察"] --> B["定位"]
    B --> C["分类"]
    C --> D["确认所有者"]
    D --> E["确认是否可重建"]
    E --> F["使用官方清理机制"]
    F --> G["重新检查 df"]
```

而不是：

```mermaid
flowchart LR
    A["磁盘满"] --> B["sudo rm -rf"]
```

## 安全清理的核心原则

### 先测量，再删除

错误：

```bash
rm -rf /some/path
```

正确：

```bash
du -sh /some/path
```

然后：

```bash
findmnt -T /some/path
```

再确认用途。

------

### 优先使用资源所有者提供的清理机制

| 数据            | 优先工具                     |
| --------------- | ---------------------------- |
| systemd journal | `journalctl --vacuum-*`      |
| Docker          | `docker ... prune`           |
| APT cache       | `apt clean`                  |
| DNF cache       | `dnf clean`                  |
| Cargo build     | `cargo clean`                |
| Flatpak runtime | `flatpak uninstall --unused` |

不要优先：

```bash
rm -rf /var/lib/xxx
```

原因是应用通常知道：

```text
哪些对象仍被引用
哪些可以重建
哪些是持久化数据
```

普通 `rm` 不知道。

------

### 删除前问三个问题

#### 谁创建了它

例如：

```text
myapp.log
```

由哪个服务写？

#### 删除后能否重建

例如：

```text
cache
```

通常可以。

但是：

```text
database volume
```

可能不能。

#### 它为什么增长

如果增长原因没有解决：

```text
清理只是延迟下一次磁盘满
```

------

### 不要把 `sudo` 当默认选项

先：

```bash
du -hd1 ~
```

只有权限不足时再：

```bash
sudo
```

特别是交互式删除工具：

```text
ncdu
gdu
dua
```

使用 root 运行意味着：

> 一个误操作可能删除系统级文件。

分析可以 root。

删除必须更谨慎。

> **应该怎么安全释放？**

可以概括为：

```mermaid
flowchart TD
    A["文件系统层<br>Where"] --> B["目录文件层<br>Who"]
```

**真正成熟的磁盘清理思路，不是掌握一条“找最大文件”的命令，而是知道什么时候应该从 `df` 切换到 `du`，什么时候应该放下 `du`，转而使用 `lsof`、`docker system df`、`journalctl` 或 Btrfs 自己的空间统计工具。**

对于大多数 Linux 用户，我建议直接记住这一条实战路径：

```bash
df -hT
df -i
sudo du -xhd1 / 2>/dev/null | sort -h
sudo dust -n 30 /var
sudo lsof +L1
```

发现具体资源类型后，**停止“盲目找文件”，切换到该资源自己的管理工具**。这通常才是既快、又安全、又适合长期运维的磁盘空间清理方法。
