## abstract

编写并发程序（Concurrent Programming）和串行程序（Serial Programming）就像是在快餐店里“单人单岗”与“多任务协作”的区别。

以下是它们在逻辑、执行效率和开发挑战等方面的关键差异：

------

###  执行逻辑与结构

这是两者最本质的区别。

- **串行执行：** 程序按严格的先后顺序执行。就像在自动洗车房，一辆车洗完，下一辆才能进来。第一步不完成，第二步永远不会开始。
- **并发执行：** 程序被划分为多个可以独立运行的任务（单元）。这些任务在时间段上重叠执行。就像餐厅里，厨师在炒菜的同时，服务员在摆餐具，收银员在结账。

###  核心区别对比表

| **特性**     | **串行执行 (Serial)**                          | **并发执行 (Concurrent)**                          |
| ------------ | ---------------------------------------------- | -------------------------------------------------- |
| **执行顺序** | 线性、确定性的。                               | 非线性、交错进行的。                               |
| **资源利用** | 较低。CPU 经常在等待 I/O（如读写文件）时闲置。 | 较高。当一个任务等待时，CPU 可以切换到另一个任务。 |
| **执行速度** | 取决于所有任务耗时的总和。                     | 在多核处理器上显著提升速度；在单核上提升响应性。   |
| **复杂度**   | 低。逻辑简单，易于调试。                       | 高。可能涉及线程安全、死锁、竞态条件等问题。       |
| **确定性**   | 结果是可预测的，输入相同，执行路径相同。       | 结果可能受“调度顺序”影响，具有随机性。             |



------

###  编程时的关键挑战（并发特有）

编写并发程序时，你需要处理串行编程中完全不存在的“副作用”：

1. **竞态条件 (Race Condition)：** 两个线程同时修改同一个数据。如果不加锁，最后的结果取决于谁“跑得快”，导致数据错乱。
2. **死锁 (Deadlock)：** 线程 A 拿着资源 1 等资源 2，线程 B 拿着资源 2 等资源 1，结果大家都在原地踏步。
3. **上下文切换开销：** CPU 在不同任务间频繁切换是需要成本的。如果并发任务过多，切换成本反而会拖慢速度。

主要问题是前2个,不过有些简单的并发任务不涉及这两个问题,例如,将一批图片进行压缩或者格式转换,每个进程或线程处理一个图片,互不干扰,通常不用考虑竞争和锁问题.

###  适用场景建议

> **串行程序：** 适用于逻辑简单的脚本、计算量极小、或者步骤之间有极强依赖关系（A 必须是 B 的前提）的任务。
>
> **并发程序：** 适用于高性能服务器、大型游戏、图形渲染，以及需要处理大量 I/O 操作（如爬虫、数据库请求）的场景。

------

## 总结

**串行**追求的是**简单与确定**，而**并发**追求的是**吞吐量与响应速度**。

现在的计算机大多是多核 CPU，编写并发程序能让你充分压榨硬件性能，但也对开发者的逻辑严密性提出了更高的要求。

## 并发和竞争

并发是否需要考虑“竞争”（Race Condition），核心取决于**多个线程是否在同时操作同一块共享且可变的数据**。

如果大家只是聚在一起“看报纸”，互不干扰；但如果大家都要抢着去“改报纸”，那就得排队了。

------

###  不需要考虑竞争的情况

在这种情况下，并发是“安全的”，你可以放心让多个线程同时跑，不需要加锁。

- **只读数据（Immutable Data）：**

  如果数据初始化后就不再改变，无论多少个线程同时读取，结果都是确定的。

  > **例子：** 多个用户同时读取网上的同一篇新闻。

- **线程私有数据（Thread-Local Storage）：**

  每个线程都拥有自己独立的变量副本，互不干涉。

  > **例子：** 每个人都有自己的笔记本，写什么都不会影响别人的本子。

- **无交集的任务（Shared-nothing Architecture）：**

  任务之间完全独立，不需要交换数据。

  > **例子：** 分布式计算中，每台机器计算不同范围的数字，最后汇总结果。

------

###  必须考虑竞争的情况

当以下三个条件**同时满足**时，竞争就发生了，你必须介入（如使用锁、信号量等）：

1. **多线程环境**。
2. **存在共享资源**。
3. **至少有一个线程在进行写操作**。

### 常见的竞争场景：

- **“读-改-写” 操作（Read-Modify-Write）：**

  这是最经典的陷阱。线程 A 读取变量，准备加 1，但在它还没写回去时，线程 B 也读取了原值。

  > 假设3个时间点:`t1,t2,t3,t4`,并且`t1<t2<t3<t4`;现在假设变量`a=0`
  >
  > 线程A,B的动作都是读取变量+1后写回;
  >
  > 现在假设线程A在t1时刻读取了变量(值为0),随后的短暂时间内线程B于时间t2读取也读取变量(此时线程A来不及将修改写回保存),读取到的也是0,因此加1后的结果也是1,在t3时刻线程A将a更改为1,而在时刻t4,线程B将1写入变量a;
  >
  > 从而导致调用的2个+1操作最终结果总共只+1,而不是+2;
  >
  > 这是一个典型的竞争问题,在并发计数中经常遇到;

- **检查后执行（Check-Then-Act）：**

  先判断某个条件是否成立，再执行操作。但在判断完之后、执行之前，条件可能已经被别的线程改了。

  > **例子：** 单例模式的延迟初始化，如果不加锁，可能会创建出两个实例。

- **复合操作：**

  比如往一个集合里添加元素，看起来是一行代码，但在底层涉及内存分配、指针移动等多步操作。

------

###  如何应对竞争

为了处理这些竞争，我们通常使用以下技术：

| **方案**                       | **原理**                               | **适用场景**                         |
| ------------------------------ | -------------------------------------- | ------------------------------------ |
| **互斥锁 (Mutex/Lock)**        | 同一时间只允许一个线程访问。           | 保护复杂的临界区。                   |
| **原子操作 (Atomic)**          | 利用硬件指令保证操作不可分割。         | 简单的计数器、状态切换。             |
| **乐观锁 (CAS)**               | 先尝试修改，如果发现中途被改了就重试。 | 高并发下的短代码块。                 |
| **消息传递 (Message Passing)** | 不通过共享内存通信，而是通过“发消息”。 | 如 Go 语言的 Channel，避免直接竞争。 |

------

## 总结

并发不等于竞争。只有当你试图让多个线程在**同一时间**、对**同一份数据**进行**修改**时，竞争这只“怪兽”才会出现。
