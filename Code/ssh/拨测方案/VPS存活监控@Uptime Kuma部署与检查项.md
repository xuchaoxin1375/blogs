## 适用前提

用 Uptime Kuma 承担**可用性监控中心**：一个网页后台维护所有代理节点的连通、端口、业务与证书检查，异常时按渠道通知，并留下历史。

它在选型中的位置与边界见主文档 `VPS存活监控方案.md` 的 **工具选型** 与 **结论** 两节。上手前需要先完成主文档里的 **VPS 侧改造**：每台 VPS 要有可断言的 `/healthz`，否则业务检查只能看状态码。

不适用的场景也应提前认清：它不做主机资源监控(CPU、内存、磁盘)，它的 Ping 延迟图也不等于专业的丢包与抖动分析。

## 部署

假设监控服务器是 Debian 或 Ubuntu，且已装 Docker Engine。用 Docker 运行，不为它单独维护 Node.js 与 PM2 运行环境。

```bash
docker volume create uptime-kuma

docker run -d \
  --name uptime-kuma \
  --restart unless-stopped \
  -p 127.0.0.1:3001:3001 \
  -v uptime-kuma:/app/data \
  louislam/uptime-kuma:2
```

| 参数 | 含义 |
| --- | --- |
| `--name uptime-kuma` | 容器名称，便于后续操作 |
| `--restart unless-stopped` | 异常退出或宿主机重启后自动恢复，除非人为停止 |
| `127.0.0.1:3001:3001` | **仅监听回环**，强制经反向代理或隧道访问 |
| `uptime-kuma:/app/data` | 命名卷持久化数据库与配置 |
| `louislam/uptime-kuma:2` | 官方 2.x 主版本标签 |

**端口写法不要改**。写成 `-p 3001:3001` 会把管理后台直接暴露到公网，且**绕过 UFW 与 firewalld** 的规则——Docker 直接改写 iptables 的 `DOCKER` 链，防火墙看着在拦，实际没拦。这是自建监控最常见的裸奔事故。

生产环境还应把镜像固定到经过验证的具体版本或摘要(Digest)，而不是长期依赖会漂移的主版本标签；升级前保存数据并写好回滚步骤。

## 首次访问：走 SSH 端口转发

后台只绑了回环，最省事的进入方式是在管理员电脑上建一条转发：

```bash
ssh -N -L 3001:127.0.0.1:3001 admin@monitor.example.com
```

| 片段 | 含义 |
| --- | --- |
| `admin` | 监控服务器的 SSH 用户名 |
| `monitor.example.com` | 监控服务器地址 |
| 第一个 `3001` | 管理员电脑本地监听端口 |
| `127.0.0.1:3001` | 监控服务器上的目标地址与端口 |

保持这条命令运行，浏览器访问 `http://127.0.0.1:3001` 即可进入初始化界面，创建管理员账号。

需要多设备远程管理时，走 WireGuard、Tailscale 一类受控网络，或**先配好 HTTPS 与身份认证**再经反代访问。无论如何都不要把管理端口直接挂在公网。

## 检查项设计

以两台承担同一业务域名的代理 VPS 为例(地址为文档示例，部署时替换)：

| 节点 | 示例 IP | 承载业务 |
| --- | --- | --- |
| `proxy-us-01` | `203.0.113.10` | `app.example.com` |
| `proxy-jp-01` | `198.51.100.20` | `app.example.com` |

初始检查项建议按下表建，重点在于**把网络层、端口层与业务层分开看**：

| 监控名称 | 类型 | 目标 | 建议间隔 |
| --- | --- | --- | --- |
| US-节点连通 | Ping | `203.0.113.10` | 60 秒 |
| US-HTTPS 端口 | TCP | `203.0.113.10:443` | 60 秒 |
| JP-节点连通 | Ping | `198.51.100.20` | 60 秒 |
| JP-HTTPS 端口 | TCP | `198.51.100.20:443` | 60 秒 |
| 公开网站健康 | HTTP(S) | `https://app.example.com/healthz` | 60 秒 |
| 公开网站证书 | HTTPS 证书 | `app.example.com` | 按工具能力配置 |

**公开网站检查是整体业务检查，不是单节点检查**。当两台 VPS 承担同一域名的流量时，域名检查只能说明入口整体可用，某台 VPS 故障后请求仍可能一直命中另一台。要测到具体节点，按主文档 **探测锚定** 一节选择做法：

- 为每台 VPS 配独立子域名，直接对子域名建 HTTPS 检查。
- 或建一条 Push 类型检查，由 VPS 侧的定时脚本按 `--resolve` 的方式自行上报。

判定顺序也有讲究：业务检查失败、但两台 VPS 的 Ping 与 TCP 都正常时，应先怀疑代理配置、源站连接、TLS、上层网关或应用响应，而不是立即判定 VPS 宕机。

## 通知配置的坑

**通知不是全局默认生效的**。创建或编辑监控项时，必须在通知区域手动勾选对应渠道——这是新手最常踩的坑，表现为"配了 Telegram 却什么都没收到"。

其余容易忽略的点：

- **状态页可以顺手做**：给站点群一个对外状态页，比口头同步状态省事。
- **维护窗口**要在计划变更前开启，否则一次重启会连着刷一串告警。
- **恢复通知**要一并验证，只报"坏了"不报"好了"会让人反复人工确认。
- **通知链路要独立测试**：在监控项全绿的状态下手动触发一次测试通知，确认渠道本身可达。国内网络环境下尤其如此，境外服务的可达性会随网络变化。

## 运维与备份

- **`/app/data` 必须持久化并纳入备份**，且要与被监控服务解耦。备份时注意一致性：数据库仍被写入时直接复制文件不可靠，应停机备份、用应用支持的备份方式，或用有快照保证的卷。
- **数据目录不支持 NFS 一类的网络文件系统**(官方说明)，不要把它放到 NAS 挂载卷上。
- **规模上限来自 SQLite**：短间隔下大约超过一两百个监控项后界面开始变卡，此时拆分实例或把检查迁到 Gatus，而不是继续往上堆。
- **镜像与版本**随升级改动，跨版本升级前先看发布说明，数据卷先备份。

## 已知局限

- **单实例无高可用**：这个实例本身挂了，告警也就停了。必须由外部 SaaS 或第二实例兜底，做法见主文档 **监控监控者**。
- **无主机资源指标**：需要看 CPU、内存、磁盘时加 Beszel 或改用哪吒，而不是指望它。
- **配置不在 Git 里**：所有检查项都在数据库里，批量创建与审计要靠界面点击；节点规模一上来，这项成本会超过部署成本。
- **单一探测位置**：所有检查都从监控服务器出发，无法自行区分"节点挂了"与"这条线路到节点有问题"，需要境外交叉探测点补位。
