## abstract

限流中有连个方面的限制,一个是连接数的限制,一个是请求数的限制

发送请求前需要建立连接,过多通常占用过多资源;

如果建立大量连接也会消耗过多资源,即便没有发送请求也会消耗资源(过多恶意连接还可能导致正常用户无法建立连接),因此完整的限流策略应该包含两者

## 一、基本概念详解

###  1. **连接数（Connection）**

- **定义**：指客户端与服务器之间建立的 TCP 连接数量。
- **特点**：
  - 一个连接可以传输多个请求（HTTP/1.1 支持 Keep-Alive）。
  - 连接是“通道”，请求是“消息”。
- **举例**：
  - 客户端访问网页 → 建立一个 TCP 连接 → 发送多个请求（HTML、CSS、JS、图片等）→ 连接保持一段时间后关闭。
  - 所以：**1 个连接 ≈ 多个请求**

> 🔹 **连接是“资源占用”的体现**：每个连接都会占用服务器的内存、文件描述符（fd）、CPU 上下文等资源。

---

###  2. **请求数（Request）**

- **定义**：指客户端通过 HTTP 协议向服务器发起的单个请求（如访问 `/api/user`）。
- **特点**：
  - 请求是应用层（HTTP）的概念。
  - 一个连接可以承载多个请求（HTTP pipelining 或 Keep-Alive）。
- **举例**：
  - 你刷新一次页面，可能发出 20 个 HTTP 请求（HTML + 资源）。
  - 一个爬虫每秒发 100 个 `/api/data` 请求，可能用了 10 个连接。

> 🔹 **请求数是“访问频率”的体现**：反映的是业务层面的调用频率。

---

## 二、形象比喻

| 类比       | 连接（Connection）                       | 请求（Request）              |
| ---------- | ---------------------------------------- | ---------------------------- |
| 快递站     | 快递员来送货的“次数”（每次来可以送多件） | 每一件包裹                   |
| 高速收费站 | 一辆车进入高速（建立连接）               | 车上载的货物（多个请求）     |
| 电话通话   | 打一次电话（连接建立）                   | 通话中说了几句话（多个请求） |

## 三、Nginx 中的限流模块

Nginx 提供了两个核心限流模块：

| 模块                         | 指令         | 作用                 |
| ---------------------------- | ------------ | -------------------- |
| `ngx_http_limit_conn_module` | `limit_conn` | 限制**并发连接数**   |
| `ngx_http_limit_req_module`  | `limit_req`  | 限制**请求处理速率** |

---

###  1. `limit_conn`：限制连接数

#### 用途
- 防止某个客户端建立过多 TCP 连接，耗尽服务器资源（如 fd、内存）。
- 适用于防止 DDoS、**连接耗尽**型攻击。

#### 配置示例

```nginx
http {
    # 按 IP 限制并发连接数
    limit_conn_zone $binary_remote_addr zone=perip:10m;

    server {
        location / {
            limit_conn perip 10;  # 每个 IP 最多 10 个并发连接
            limit_conn_status 429;
        }
    }
}
```

> 📌 如果一个 IP 同时打开 15 个标签页请求资源，超过 10 个就会被拒绝。

---

###  2. `limit_req`：限制请求数

#### 用途
- 控制单位时间内的请求频率（如每秒最多 10 个请求）。
- 适用于 API 限流、防刷、防爬虫。

#### 配置示例

```nginx
http {
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;

    server {
        location /api/ {
            limit_req zone=one burst=20 nodelay;
            limit_req_status 429;
        }
    }
}
```

> 📌 使用“令牌桶”算法：每秒生成 10 个令牌，最多积压 20 个请求。

---

## 四、区别与互补

| 维度         | `limit_conn`（连接） | `limit_req`（请求）      |
| ------------ | -------------------- | ------------------------ |
| **控制目标** | 并发连接数           | 请求处理速率             |
| **防什么**   | 连接耗尽、DDoS       | 请求刷屏、爬虫、API 滥用 |
| **单位**     | 同时存在的连接数     | 时间内的请求数（如 r/s） |
| **粒度**     | 较粗（连接级）       | 较细（请求级）           |
| **典型场景** | 静态资源、下载站     | API 接口、登录页         |



因为攻击或滥用可能从不同维度发生：

| 攻击类型                            | `limit_conn` 能防 | `limit_req` 能防 |
| ----------------------------------- | ----------------- | ---------------- |
| 单 IP 建立 1000 个连接              |                   | ❌                |
| 单连接高频发请求（HTTP pipelining） | ❌                 |                  |
| 多连接并发刷接口                    | +                 | +                |

> 🔥 **最佳实践：组合使用，立体防护**



```nginx
location /api/ {
    limit_conn perip 5;        # 每个 IP 最多 5 个并发连接
    limit_req zone=api burst=10 nodelay;  # 每秒最多 10 个请求（突发允许 10 个）
    limit_req_status 429;
    limit_conn_status 429;
}
```

### 浏览器中打开两标签访问同一个链接会建立几个连接?

在浏览器中**同时打开两个标签页访问同一个链接**（即相同的 URL），浏览器**是否会建立多个网络连接**，取决于多个因素，包括资源类型、缓存策略、连接复用机制等。

> 通常情况下，**浏览器会复用已有的 TCP/TLS 连接（如 HTTP/1.1 Keep-Alive 或 HTTP/2 多路复用）**，  
> 所以**不一定建立多个物理连接**，但**是两个独立的请求**。



#### 1. **这是两个独立的请求**

即使 URL 相同，**每个标签页发起的请求是独立的**：
- 浏览器会为每个标签页分别发起 HTTP 请求。
- 服务器会收到两个独立的请求，可以分别响应。

> 📌 每个标签页 = 独立的浏览上下文 = 独立的请求。

---

#### 2. **是否会建立两个 TCP 连接？**

这取决于协议和连接复用机制：

| 协议                      | 是否复用连接               | 说明                                                         |
| ------------------------- | -------------------------- | ------------------------------------------------------------ |
| **HTTP/1.1 + Keep-Alive** | ✅ 可能复用，也可能新建     | - 如果第一个请求已完成，连接可能仍保持（短暂），第二个请求可复用。<br>- 但 HTTP/1.1 通常对同一域名限制 6 个并行连接，且不能多路复用。 |
| **HTTP/2**                | ✅ 复用单个连接             | - HTTP/2 支持多路复用（Multiplexing）。<br>- 即使两个标签页同时请求同一 URL，也**通过同一个 TCP 连接发送两个请求**，效率更高。 |
| **HTTP/3 (QUIC)**         | ✅ 基于 UDP，连接复用更高效 | - 使用 QUIC 协议，连接建立更快，支持多路复用，两个请求可通过同一个 QUIC 连接传输。 |

> ✅ 所以：**物理连接可能只有 1 个，但逻辑请求是 2 个**。

---

#### 3. **缓存的影响**
如果资源**已缓存**（内存或磁盘缓存），浏览器**可能根本不会发起网络请求**。

- 例如：静态资源（JS、CSS、图片）设置了 `Cache-Control: max-age=3600`
- 第二个标签页打开时，直接从缓存加载，**不建立任何网络连接**

> 📌 只有**未缓存或强制刷新**时，才会真正发送请求。

---

#### 4. **Cookie 和会话是否共享？**
- ✅ 同一域名下的两个标签页**共享 Cookie 和 LocalStorage**
- 所以如果网站依赖会话（Session），两个标签页会**使用同一个用户会话**
- 但每个请求仍是独立的，服务器会分别处理

---

###  实验验证方法

你可以在浏览器开发者工具中验证：
1. 打开 **Network** 面板
2. 在两个标签页中打开同一个 API 链接（如 `https://api.example.com/user`）
3. 查看：
   - 是否有两个请求记录
   - 是否复用连接（看 `Protocol` 列：h2 表示 HTTP/2，复用连接）

---

✅ 总结

| 问题                   | 回答                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 会发起几个请求？       | ✅ **两个独立的 HTTP 请求**                                   |
| 会建立几个 TCP 连接？  | ⚠️ **不一定**，取决于协议：<br>- HTTP/1.1：可能 1~2 个（连接池）<br>- HTTP/2+：通常 **1 个连接复用** |
| 是否真的发送到服务器？ | ✅ 是，除非资源被缓存                                         |
| 是否共享会话？         | ✅ 是，共享 Cookie 和登录状态                                 |
