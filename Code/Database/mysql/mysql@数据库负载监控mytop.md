## abstract

[mytop(1) - Linux man page](https://linux.die.net/man/1/mytop)

mytop - display MySQL server performance info like 'top'

一份系统的 **`mytop` 阅读指南**能帮助你快速区分数据库是“正在忙碌”还是“已经瘫痪”。`mytop` 的界面通常分为三部分：**头部概况（Header）**、**统计明细（Statistics）** 和 **实时进程列表（Processlist）**。

------

##  核心快速识别表

| **异常状态**   | **表现指标**                                           | **优先级** |
| -------------- | ------------------------------------------------------ | ---------- |
| **系统过载**   | `load` 远大于 CPU 核数，`Threads Running` 接近 `Total` | 紧急 🔴     |
| **存在慢查询** | `Slow` 计数持续跳动，`Slow qps` 数值大                 | 重要 🟠     |
| **连接数爆炸** | `Threads` 总数接近 `max_connections` 配置              | 紧急 🔴     |
| **写压力大**   | `Se/In/Up/De` 中 `In/Up/De` 的占比显著提高             | 关注 🟡     |

------

## 第一部分：头部概况 (System Header)

这一行展示的是服务器操作系统的整体健康状况。

> **示例：** `MySQL on localhost (8.0.35) load 43.29 34.25 30.27 12/2585 2545166 up 0+14:45:25 [11:13:01]`

- **MySQL version**: 括号内的数字。用于确认特性（如 8.0 支持窗口函数，5.7 性能较稳）。
- **Load Average**:
  - **阅读法则**：数值除以 CPU 核心数。$> 1.0$ 说明有排队，$> 5.0$ 通常意味着系统响应变慢。
  - **三个数字**：分别代表 1、5、15 分钟。如果 $1min > 15min$，压力在增加。
- **up (Uptime)**: 数据库运行时间。时间太短说明可能刚崩溃过。

------

## 第二部分：性能统计 (Performance Statistics)

这几行是数据库内核的性能快照。

### 1. 查询效率

- **Queries**: 总查询数。
- **qps**: 全局平均每秒查询数。
- **qps now**: **最重要的实时指标**。反映当前的瞬时压力。
- **Slow**: 慢查询累计总数。
- **Slow qps**: **实时监控重点**。如果这个数字很大（如 $> 5$），说明当前有大量垃圾 SQL 正在执行。

### 2. 读写比例 (Se/In/Up/De)

- **格式**: Select / Insert / Update / Delete 的百分比。
- **解读**:
  - `95/01/00/01`：读密集型（适合增加缓存、读写分离）。
  - `50/20/20/10`：混合型（需关注锁竞争和 IO 压力）。

### 3. 线程状态 (Threads)

- **格式**: `Total ( Running / Cached )`
- **Total**: 当前客户端连接总数。
- **Running**: **核心指标**。真正正在处理请求的线程。如果这个值长期居高不下，说明 SQL 被卡住了，或者 CPU 已经算不过来了。

### 4. 网络与缓存 (Key Efficiency / Bps)

- **Key Efficiency**: 索引缓存命中率。通常应 $> 90\%$。如果太低，说明索引没起作用或者内存（`key_buffer_size`）分配不足。
- **Bps in/out**: 每秒入站/出站流量。`out` 远大于 `in` 是常态，因为结果集通常比 SQL 语句大。

------

## 第三部分：实时进程列表 (Processlist)

这部分告诉你“是谁在干坏事”。

| **字段**      | **说明** | **关注点**                                                   |
| ------------- | -------- | ------------------------------------------------------------ |
| **Id**        | 进程 ID  | 杀掉进程用 `kill <Id>`。                                     |
| **User/Host** | 来源     | 哪个账号、哪个 IP 来的请求？（定位是哪个业务模块）。         |
| **DB**        | 数据库名 | 哪个数据库当前压力最大。                                     |
| **Time**      | 持续时间 | **重点**。数值越大，说明该查询卡住的时间越久。               |
| **State**     | 状态     | `Sending data` (找索引)、`Locked` (等锁)、`Sorting` (排序耗 CPU)。 |
| **Query**     | SQL 语句 | 具体的 SQL 文本，优化代码的核心线索。                        |

------

## 💡 进阶使用小技巧 (快捷键)

在 `mytop` 运行界面按以下键：

- **`d`**: 切换显示特定数据库的进程。
- **`f`**: 查看某个特定线程的完整 SQL 语句。
- **`k`**: 杀死一个线程（输入 ID）。
- **`p`**: 暂停屏幕刷新（方便仔细阅读 SQL）。
- **`o`**: 反转排序顺序。
- **`q`**: 退出。

------

## 总结：你的阅读逻辑顺序

1. **看 Load**：服务器是不是要爆了？
2. **看 Threads Running**：有多少人在排队干活？
3. **看 Slow qps**：是不是有烂 SQL 拖后腿？
4. **看 Processlist**：是谁（User）、在哪（Host）、用什么（Query）把数据库搞死的？

## 案例

```bash

MySQL on localhost (8.4.8)                                                                                                                                                 load 21.35 19.30 18.75 24/2292 3538978 up 3+00:13:47 [10:05:09]
 Queries: 2.0G     qps: 8140 Slow:   399.0         Se/In/Up/De(%):    96/01/00/00
 Sorts:  11957 qps now: 6963 Slow qps: 0.0  Threads:   25 (   8/ 289) 97/01/00/00
 Key Efficiency: 99.3%  Bps in/out: 969.3k/28.7M   Now in/out: 888.1k/25.7M
```

这份数据展示了 MySQL 数据库在某一时刻的运行状态快照（通常来自 `mytop` 或类似的监控工具）。

目前来看，你的数据库正处于**高负载运行状态**，且表现出极强的**读多写少**特征。以下是详细的解读：

------

### 1. 系统基础信息

- **MySQL on localhost (8.4.8):** 运行在本地的 MySQL 8.4.8 版本（这是一个较新的 LTS 版本）。
- **Load 21.35 19.30 18.75:** 系统的平均负载（1/5/15分钟）。**警告：** 负载超过 20 通常意味着 CPU 非常繁忙。如果你的服务器只有 16 核或更少，说明系统已经出现排队拥堵。
- **Up 3+00:13:47:** 数据库已连续运行了 3 天 13 分钟。

### 2. 查询性能 (Queries & QPS)

- **Queries: 2.0G:** 自启动以来累计处理了 20 亿次查询。
- **qps: 8140:** 平均每秒查询数（QPS）为 8140。
- **qps now: 6963:** **当前**这一秒的 QPS 为 6963。这是一个非常高的负载，属于高并发场景。
- **Slow: 399.0:** 累计慢查询 399 条。相对于 20 亿的查询总量，这个数值极低，说明大部分查询效率很高。

### 3. 操作占比 (Se/In/Up/De)

- **96/01/00/00:** 这是最关键的数据。
  - **Select (查询): 96%**
  - **Insert (插入): 1%**
  - **Update (更新): 0%**
  - **Delete (删除): 0%**
- **结论：** 这是一个极其典型的**读密集型**应用（如新闻门户、产品展示页或只读 API）。你的优化重点应完全放在查询缓存、索引优化和从库扩展上。

### 4. 线程与连接 (Threads)

- **Threads: 25 (8/289):** * 当前有 **25** 个活动连接。
  - 其中 **8** 个线程正在运行（Running），其余在睡眠（Sleep）。
  - **289** 是线程缓存（Thread Cache）的大小。
- **解读：** 虽然 QPS 很高，但活跃线程并不多，说明单个查询的执行速度非常快，没有产生堆积。

### 5. 缓存与网络 (Efficiency & Bandwidth)

- **Key Efficiency: 99.3%:** 索引缓存命中率。非常优秀，说明索引几乎都在内存中，磁盘 I/O 压力较小。
- **Bps out: 28.7M (Average) / 25.7M (Now):** * 数据库每秒向外发送约 **25MB - 28MB** 的数据。
  - 在高并发下，你需要注意服务器的网卡带宽是否会成为瓶颈（例如千兆网卡的上限约 125MB/s）。

------

### 💡 总结与建议

1. **性能表现：** 你的数据库目前表现得**非常稳健**。尽管 Load 很高，但慢查询极少，索引命中率极高，说明配置和索引优化得相当不错。
2. **潜在风险：** **系统负载 (Load) 偏高**。如果 Load 持续上升，建议检查是否是某个特定的复杂 SQL 占用了过多的 CPU，或者考虑增加 CPU 核心。
3. **优化方向：** 既然 96% 都是查询，后续如果性能遇到瓶颈，优先考虑增加 **Redis 缓存层** 或增加 **只读从库 (Read Replicas)** 来分担主库压力。
