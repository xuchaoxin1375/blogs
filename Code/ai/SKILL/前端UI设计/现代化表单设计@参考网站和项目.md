## 一、先看表单设计规范

### 1. GOV.UK Design System

我最推荐作为第一站。

它的特点不是视觉时髦，而是把复杂业务表单拆解得非常清楚，包括：

- 如何组织长表单
- 什么时候一页只问一个问题
- 日期、地址、姓名等字段如何设计
- 错误摘要和字段错误如何配合
- 多步骤表单如何显示进度
- 如何降低用户的理解成本

重点阅读 **Structuring forms**、Text input、Error message、Error summary、Date input、Radios、Checkboxes 等章节。([design-system.service.gov.uk](https://design-system.service.gov.uk/?utm_source=chatgpt.com))

**适合借鉴：**政务系统、后台系统、开户申请、保险、医疗、复杂资料填写。

## 三、适合阅读源码的项目和技术方案

### React 技术栈

#### React Hook Form

适合学习生产项目中的表单状态管理：

- 字段注册
- touched、dirty、valid 等状态
- 表单提交
- 动态字段
- 数组字段
- 异步校验
- 与 UI 组件库集成

它更偏“表单数据和状态管理”，不会替你解决所有 UX 设计问题。([React Hook Form](https://www.react-hook-form.com/?utm_source=chatgpt.com))

推荐搭配：

**React Hook Form + Zod + 自己的 Field 组件封装**

Zod 可以将运行时校验规则和 TypeScript 类型联系起来，适合建立统一的数据 Schema。([Zod](https://zod.dev/?utm_source=chatgpt.com))

------

#### React Aria / React Spectrum Forms

非常值得研究它对以下问题的处理：

- 可见 label 和辅助说明
- 原生 HTML 约束校验
- 自定义校验
- 实时校验
- 服务端错误
- 提交失败后聚焦第一个错误字段
- 屏幕阅读器反馈

React Spectrum 的表单文档还展示了 React Hook Form 的集成方式。([react-spectrum.adobe.com](https://react-spectrum.adobe.com/forms?utm_source=chatgpt.com))

它特别适合帮助你理解：一个真正完整的 `FormField` 组件，不应当只有输入框和红色边框。

------

### Vue 技术栈

#### VeeValidate

适合学习 Vue 3 中：

- `useForm`
- 字段状态管理
- 表单提交
- Schema 校验
- 自定义输入组件
- 与组件库集成
- Zod、Yup 等验证方案

它既支持组件方式，也支持 Composition API，比较适合从简单表单逐渐过渡到复杂业务表单。([vee-validate.logaretm.com](https://vee-validate.logaretm.com/v4/api/form/?utm_source=chatgpt.com))

### 动态表单和低代码方向

#### Formily

阿里开源的表单解决方案，支持 React、Vue、React Native，以及 JSON Schema 驱动的动态表单和表单设计器。([GitHub](https://github.com/alibaba/formily?utm_source=chatgpt.com))

建议重点研究：

- Schema 如何描述字段
- UI Schema 与数据 Schema 如何分离
- 字段联动
- 显示、隐藏和禁用条件
- 表单路径和嵌套结构

## 四、建议你重点建立的表单知识地图

看到任何表单案例时，可以从这八个维度分析：

| 维度   | 需要观察的问题                             |
| ------ | ------------------------------------------ |
| 任务   | 用户为什么要填写，完成后能获得什么         |
| 结构   | 字段是否合理分组，顺序是否符合用户思维     |
| 控件   | 是否选择了正确的输入类型                   |
| 文案   | Label、示例、帮助文字是否清楚              |
| 状态   | 默认、聚焦、填写、错误、禁用、加载是否完整 |
| 校验   | 什么时候校验，错误是否说明如何修复         |
| 恢复   | 提交失败、刷新、返回后数据是否保留         |
| 无障碍 | 键盘、焦点、语义、读屏和错误通知是否可用   |

其中最容易被初学者忽略的是：

- 不要用 placeholder 代替 label
- 不要在用户刚输入第一个字符时就显示错误
- 错误提示要说明“哪里错了”和“如何修复”
- 前端校验不能代替服务端校验
- 提交失败后不能只弹一句“提交失败”
- 自定义 Select、DatePicker、Combobox 要特别注意键盘和读屏行为

W3C、Carbon 和 React Spectrum 的资料都对标签、帮助信息、校验及无障碍反馈提供了较完整的实现参考。([W3C](https://www.w3.org/WAI/tutorials/forms/?utm_source=chatgpt.com))

## 2. 不要寻找一个“完美参考”

建议每次找三个不同角色的参考：

| 参考类型 | 解决什么问题                  |
| -------- | ----------------------------- |
| 结构参考 | 字段顺序、分组、步骤划分      |
| 交互参考 | 校验、Loading、保存、错误处理 |
| 视觉参考 | 字体、间距、颜色、圆角、布局  |

例如做一个创建项目表单：

- 结构参考：Linear 的创建 Issue 流程
- 交互参考：Stripe 的字段校验和提交反馈
- 视觉参考：Vercel 的简洁深色风格

这样向 agent 表达时不要说：

> 完全模仿 Linear。

而要说：

> 使用 Linear 式的紧凑字段结构；采用 Stripe 式的错误反馈；视觉上参考 Vercel，但保留当前项目的颜色变量。

这能显著减少 agent “抄错重点”。

## 4. 给 coding agent 的需求应包含什么

一个容易失控的需求通常是：

> 帮我做一个现代、简洁、高级的注册表单。

“现代”“高级”无法验收。Agent 只能猜。

更好的表达应包含七部分：

### 背景

说明这个页面属于什么产品、谁使用、目标是什么。

### 流程

说明用户进入页面后按什么顺序操作，成功和失败后去哪里。

### 字段

说明字段类型、是否必填、默认值和数据结构。

### 状态

至少描述：

- Default
- Hover
- Focus
- Filled
- Invalid
- Disabled
- Submitting
- Success
- Server error

### 校验

明确：

- 校验条件
- 校验时机
- 错误文案
- 服务端错误如何映射到字段

### 视觉方向

不要只使用形容词，要给出可执行参数：

- 最大宽度
- 单列还是双列
- 间距体系
- Label 位置
- 圆角范围
- 是否使用阴影
- 主按钮位置
- 桌面端和移动端差异

### 验收标准

把需求写成可以判断“通过或不通过”的句子。

## 7. 一个很有效的 Agent 协作方法

不要一上来就让 agent 完成全部页面。分三轮通常更稳。

### 第一轮：只分析

> 检查现有项目的组件、依赖和设计 token。根据需求给出页面结构、组件树、状态模型和文件修改计划，暂时不要编码。

### 第二轮：实现骨架

> 实现页面布局、字段组件和响应式结构，暂时使用本地提交函数，不连接真实接口。确保所有状态在 Storybook 或测试页面中可观察。

### 第三轮：连接业务

> 接入真实 Schema、API、服务端错误映射、成功跳转和测试。不要修改已经确认的视觉结构。

这种方式能防止 agent 在视觉、业务逻辑、接口和重构之间同时发散。
