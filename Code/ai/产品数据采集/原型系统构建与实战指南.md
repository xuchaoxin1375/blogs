## 系统概览：从选型文档到可运行原型

前篇《AI驱动的产品数据采集系统设计指南》完成了选型论证；本文记录把结论落成**可操作、可实战**的原型系统（`C:\repos\blogs\crawl-system`，独立git仓库）的过程与实测结果。构建时间2026-10-26/27，所有结论均来自当日真实站点实测，文末附诚实的验收清单（已验证/未验证/已知问题）。

系统沿用四层架构，关键落地决策：

| 层 | 原型实现 | 说明 |
| --- | --- | --- |
| 规则生成层 | `AGENTS.md`＋`.opencode/skill/`两个技能＋`memory/lessons.md`效率闭环＋`probe_site.py`侦查工具 | opencode（v2.1.4）非交互式`opencode run`实测可用；不绑harness |
| 规则运行层 | `engines/`四档引擎（引擎与规则分离）：`shopify_api`（接口档）、`sitemap_static`（静态档）、`listing`（列表分页档）、`stealth`（scrapling隐身档） | 站点包瘦身到`spec.yaml＋parse.py＋3行spider.py` |
| 任务控制层 | Track A：`crawlctl.py`（文件状态机CLI）；Track B：`api.py`（FastAPI REST，共用同一套控制函数） | 双路开发供对比 |
| 数据分析层 | SQLite（products最新视图＋snapshots只追加历史＋runs运行记录）；GUI A：Streamlit面板；GUI B：FastAPI＋原生前端 | 数据层双GUI共用 |

与设计文档的**三处修正**（实测驱动）：
- 运行层主选Crawlee的结论不变，但**Scrapling 0.5的定位上修**：其`StealthySession`（patchright隐身Chrome，不是旧版Camoufox）＋`solve_cloudflare`实测能解CF managed挑战，且**解一次挑战后连`/products.json`都能直调**——形成了"stealth_browser＋api_json混合档"这一新档位。
- SQLite作为默认存储（arena构建规范建议＋零部署），PostgreSQL留作多人协作升级路径。
- "规则形式"混合方案被实战进一步支持：**列表选择器这类"what"确实可以下沉到spec.yaml声明式配置**（listing档），解析"how"留在代码。

## CF验证站的完整解法（本次最有价值的实战发现）

claires.com的解题链路，每一环都实测验证：

1. **侦查**：impit（Firefox 133指纹HTTP客户端）访问任何URL均403 Cloudflare挑战 → 判定stealth档；
2. **解挑战**：`StealthySession(headless=True, solve_cloudflare=True)`约**60秒自动解开managed挑战**（scrapling 0.5内置patchright隐身Chrome）；
3. **会话复用**：解一次后cookie对全站有效——站点地图、商品页连续抓取16/16全部200，无再次挑战；
4. **识别真身**：商品页无JSON-LD → 引擎**转存HTML到`runs/<site>/last_page.html`**（解析失败的调试回路）→ 从`productVariants`数据岛和cdn.shopify.com图片识别出**其实是Shopify店**；
5. **混合档**：解过挑战的会话直接调`/products.json`（200合法JSON）→ `spec.yaml`加一行`api: products_json`即切换为"隐身＋接口"混合模式，6商品完整入库。

**边界也要如实记录**：autoparti.it的CF把挑战从managed升级到interactive再到embedded——首页挑战最终被patchright解掉，但该站无有效sitemap，原型未继续（URL发现源缺失时应退回列表分页档）。**CF可解≠可采**；hm.com（Akamai＋地理入口＋全异步）则按用户指示放弃——隐身浏览器不是银弹，住宅代理才是那一级的答案。

## 站点地图有效性与多语言市场

**站点地图有效性**是`probe_site.py`侦查的一等公民，判定链为：发现（robots.txt的Sitemap行→/sitemap.xml→/sitemap_index.xml）→ XML解析（含`.xml.gz`）→ 类型（sitemapindex/urlset）→ URL数与lastmod新鲜度 → **抽样2条URL实测HTTP 200**。实测案例：lords-electrical的robots.txt是404但`/sitemap.xml`有效（不能只信robots）；其子图为`.xml.gz`（2001条URL，抽样2/2可访问）；claires的sitemap在CF后面（隐身会话才能读）；boutiqueauto的"/en/sitemap.xml"返回HTML错误页（verdict=broken，实测正确）。无有效地图时走`engines/listing.py`列表分页档——选择器写在spec.yaml（声明式），解析仍是纯函数。

**多语言市场**：probe用三层证据发现市场入口（hreflang标签＋sitemap URL语言前缀统计＋常见locale路径实测），boutiqueauto发现9个市场、fink-store发现7个。市场切换在运行时完成：`crawlctl start fink-store --market de`→环境变量`MARKET`→start_urls取`/de/`前缀→`/de/products.json`，数据按`(site, market, handle)`主键隔离。德语市场实测5条商品（"LUGANO WC-Bürste"等）。**同一引擎零修改换市场**，这是对"多语言市场下采集目标语言数据"需求的直接回答。另注意：市场路径未必是简单前缀（PrestaShop不同语言的分类slug不同），复杂站点需要按市场探测入口URL。

## Agent工作流与效率闭环

**接入方式**（opencode实测，其他harness同理）：项目`AGENTS.md`定义标准流程（侦查→定档→定URL来源→写包→小规模试跑→收尾记录）；技能目录`.opencode/skill/`放两个技能：

- `crawl-site/SKILL.md`：本项目**实测验证**的API片段（crawlee 1.11的`ConcurrencySettings`三参坑、`CRAWLEE_PURGE_ON_START`；scrapling 0.5的`StealthySession`用法与CF判据；impit无`.close()`、gzip要用`.content`等）；
- `scrapling-official/SKILL.md`：**Scrapling官方Agent Skill**（26KB，AgentSkills规范），官方自述目的是"让agent用当前API而不是凭过时训练数据猜测"。

**MCP评估**：`scrapling mcp`（stdio）握手实测成功，提供**16个工具**（browser_open/browser_fetch/browser_extract/browser_network_requests/会话管理等）。价值判断：`browser_network_requests`能直接抓到页面的XHR请求列表——对"找JSON接口"这类探查是刚需能力；配合`browser_save_state`可保存登录态。适合作为可选增强挂在harness上（opencode的mcp配置即插即用），本项目流程未依赖它（CLI优先原则不变）。

**效率闭环机制**：`memory/lessons.md`由规约强制"开工前读、收工后追加"。实测效果：第一个站点包（curiousmindsbusybags）耗时约40分钟（含引擎泛化），到fink-store仅**约10分钟**（复用模式：只改spec＋BASE）。

## 双路开发对比结论

| 轴 | Track A | Track B | 结论 |
| --- | --- | --- | --- |
| 任务控制 | `crawlctl.py`文件状态机CLI（实测start/pause/resume/kill/purge） | `api.py`FastAPI封装同一套函数＋REST | **本质是同一实现的两层皮**：CLI是最大公约数（agent和面板都调它），REST是Web化出口。建议保留CLI为唯一事实源，API薄封装 |
| 图形界面 | Streamlit面板（约60行，控件级状态闭环，每个按钮回显真实JSON） | FastAPI＋原生前端（单HTML，浅/深色适配，加载/空/错误态，15秒轮询） | 原型期Streamlit最快；要精细交互与多人访问时迁FastAPI＋React（GUI B的`/api`契约即迁移路径）。本原型两者并存共用同一数据与控制层 |
| 运行框架 | crawlee承担三个非隐身档（队列持久化/并发限速/去重续跑内建） | scrapling承担隐身档（浏览器会话/CF求解） | **不是二选一而是分档共存**：crawlee做"编排与运维底座"，scrapling做"困难站的浏览器手"。融合点已实现（stealth引擎的暂停标记/礼貌间隔/入库与crawlee档完全一致） |

## 诚实验收清单

**已验证**（真实执行过）：
- 五档引擎在7个真实站点跑通，三市场（us/uk/de）合计入库逾千条商品；
- `crawlctl`全流程（mock与真实站点）＋中文Windows的tasklist GBK修复；
- REST控制闭环（start/pause冲突409/resume/kill/purge/404未知站）；API触发的全量采集1000条/12秒；
- **真实站点暂停/恢复闭环**：`start --max-items 60`→48秒暂停（11条落库）→resume断点续跑（"启动/暂停/恢复"用户操作全链路）。**resume语义**：只消化暂停前已入队未处理的请求（实测暂停时队列余9个详情页→resume跑完9条即finished），不重新做列表发现；要发现新商品用`start --fresh`（upsert按site+market+handle保证不重复）；resume不传`max_items`时回落spec.limits（续跑沿用包内限额）；
- CF managed挑战自动求解（claires，约60秒）＋挑战后会话直调products.json（混合档）；
- 无有效sitemap站的列表分页档（lighting2lightbulbs，Magento，含gtin/mpn字段）；
- 多语言市场切换（fink-store `MARKET=de`→`/de/products.json`→德语商品入库）；
- Streamlit与FastAPI前端HTTP 200＋渲染无异常；Scrapling MCP握手＋16工具枚举；
- opencode技能加载与规约约束（4轮日志证据）＋1轮完整agent验收（gtin12缺陷发现与修复）；
- 存储层三件套（autocommit＋用完即关＋WAL）经"写入即读回＋多进程并发"实测校准。

**GUI点击级自动化验收（2026-10-27，用户反馈"页面不行"后补做）**：两个面板各抓到并修复一个HTTP冒烟测不出的真bug——
- **Streamlit面板**：数据分析tab对sqlite3连接误用duckdb风格`.df()`→页面直接抛AttributeError（此前curl 200完全没暴露）。修复为pandas DataFrame转换；顺带修复：默认选中无数据站点（有数据的站排前）、按钮点击后状态区滞后一次渲染（`st.rerun()`＋`session_state`保留操作反馈）、run.log的ANSI颜色码清理。
- **FastAPI前端**：`loadSites()`把加载动画写入nav卡片parentElement，把承载站点列表的`<ul>`从DOM替换掉——站点列表永远不可见而数据其实已加载。修复后6站点正常渲染。
- 修复后回归（浏览器自动化走点击流）：Streamlit的start（真实重采1001条落库）/pause（对finished任务正确409错误提示）/resume/kill全流程＋数据分析与运行日志渲染；FastAPI的站点切换/质量报告/23条真实数据表/pause 409错误提示。
- **方法论**：SPA/流式UI（Streamlit、WebSocket页面）的验收必须用浏览器自动化走点击流——HTTP 200冒烟证明不了任何交互可用性。

**未验证**（如实声明）：
- browser档（纯PlaywrightCrawler动态站）未在真实困难站验收（hm.com被用户放弃；boutiqueauto的AJAX列表未继续）；
- Linux/macOS分支（进程组信号、路径）未实机测试；

**已知问题**：
- ~~孤儿runs行~~ 已修复：`begin_run`自动清理同站遗留的running行；`crawlctl start --max-items`与REST `max_items`参数已补齐（试跑限量标准入口）；
