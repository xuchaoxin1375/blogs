# 四步把 SOP 变成 Agent 工作流

## 核心观念：任务拆解（Task Decomposition）

前沿模型的能力已经够强，但许多人仍觉得模型表现不佳或产出不靠谱。根据咨询经验，大多数问题出在"不知道如何把一个大任务拆成 agent 可跑得动的小任务"。

- 技术人员：好的任务拆解能力可以构建更稳定的系统
- 非技术人员：必须知道如何把日常执行项目拆小块委派给 AI，而不是整包丢进去

---

## 三个关键名词定义

### 1. Human SOP（传统流程文件）

写给人看的流程文件，告诉你第一步做什么、第二步做什么、遇到例外怎么处理。

- 形态：可能是简报、Word 文档
- 特点：旁边有一堆小提醒和经验谈
- 人类阅读时脑中会**自动补 context**，自行判断哪一步可以偷懒、哪一步一定要做

**举例**：SOP 写"申请完之后送主管签核"
- 人类会自动判断：200 元以内小金额，主管不希望被打扰，直接跑完流程
- 超过 5000 元：照规矩来，至少口头知会主管

**问题**：这种 SOP 对 agent 来说是一坨非结构化的文字
- 理解成本高，执行时容易望文生义
- AI 不会自行判断 200 元 vs 5000 元的差异
- 不知道哪一步可以省略，不知道遇到例外要继续做还是停下来问人

### 2. Skill

把做事的方法论、判断标准、踩过的坑打包成一个资料夹交给 agent。

**Skill 资料夹通常包含三个东西**：

| 组成 | 说明 |
|------|------|
| **skill markdown** | 人类写给 agent 的 SOP 加上判断方法，是 skill 的核心文件 |
| **references** | 额外的参考资料（范例输出、术语表、过去踩坑记录），agent 可自行取用 |
| **scripts** | 可以直接执行的脚本，处理确定性操作（档案处理、格式转换等传统软体工程能做到的事） |

**关键特性**：
- 一个 skill 对应**单一任务**，不是整条工作流
- 常用命名：`weekly_report_drafting`、`pdf_processing`、`invoice_categorization`
- **防守范围（scope）要适中**：
  - 太大 → 样样通但都做不好
  - 太小 → 每走一步都要读 skill，等于把模型当小孩

### 3. Agentic Workflow

由多个 agents、tools、skills、资料源组成的工作流。

- 不是单纯的 prompt，是一条**生产线**
- 有人负责理解问题，有人查资料，有人执行动作，有人写报告
- 中间调用各种工具、API、资料库、已写好的 skills

**本质比喻**：一间工厂，里面全是 AI 伙伴在帮你做事

### 三者关系统整

| 类型 | 对象 | 本质 |
|------|------|------|
| Human SOP | 给**人**看 | 传统流程文件 |
| Skill | 给 **agent** 执行 | 流程 + 方法论的执行单位 |
| Agentic Workflow | 整条任务 | 多个 skill + 工具串成的生产线 |

## 为什么不能用 Mega Agent？

### 生活化比喻：打扫家里

请帮手打扫家里，只说"把家里打扫干净"：
- 你心目中的干净：地板不粘脚、桌面清爽、厨房水槽清、垃圾倒掉
- 帮手心目中的干净：东西归位就好，角落柜子后面不用特别动
- 结果：你在意的地方一个都没动到

**问题从来不是帮手够不够聪明，而是没告诉他你在想什么。**

### AGI 也解决不了

就算有一天出现跟真人一模一样的 AI 居家帮手，还是得跟他磨合：
- 第一个月：知道你极简主义，桌面只要必要的东西
- 第二个月：知道你爱惜不粘锅，刷的时候用菜瓜布黄色那一面

这些事没写在任何说明书上，但你很在意，不知道这些事的机器人再聪明都像笨蛋。

### Mega Agent 的失败模式

第一次接触 agent 的人直觉就是：找最强的模型，把任务整包丢给他，从头跑到尾。这就是 **mega agent**。

**风险**：
- 可能写洋洋洒洒的优化建议
- 可能改一堆 config 档
- 可能 refactor 一个根本不该动的模组
- **中间发生什么，你看不见**，想 review 也找不到起点

**新手的错误反应**：换更强的模型、写更详细的 prompt。但问题不在模型或 prompt，而是**任务本身太大太模糊**。

## Divide and Conquer：小任务的力量

### 对比示例

**Mega Agent 做法**：处理客户 ticket 整包丢给一个 agent

**正确做法**：拆成 4 个 agent

| Agent | 职责 |
|-------|------|
| Agent 1 | 只负责分类 |
| Agent 2 | 只负责查资料库，找出相关历史记录 |
| Agent 3 | 只负责写回复草稿 |
| Agent 4（subagent） | 专门做 QC，确认回复有无事实错误或政治不正确 |

**每个 agent 或许都很笨，但都做一件很明确的事。**
- 出错时，看 log 发现是分类时把客诉判定为咨询需求 → 改分类的 SOP 就好
- 不需要动查资料的、写回复的、QC 的
- **哪里坏改哪里，对症下药**

### 企业级框架的核心逻辑

大公司不直接用 mega agent，因为他们要上 production，需要：
- **稳定性**
- **可观测性**
- **可修复性**

看不到内部的黑箱，永远没办法 production ready，因为你根本不敢让他上线。

> Divide and Conquer（分而治之）这个古老观念，在 agent 时代反而更重要。你不是在训练一个超人 agent，而是在**设计一条生产线**。

## 四步方法论：Human SOP → Agentic Workflow

用"洗衣服"当贯穿案例。

### 原始 Human SOP

> "把衣服丢进去，加洗衣精按开始，等洗完之后，把衣服拿去晒"

**人类看得懂**因为脑中会自己补判断：
- 白衬衫最好分开洗，不然被牛仔裤染色
- 毛衣不能丢洗衣机要手洗，否则会缩水
- 天气不好就用烘衣机，不用晾的

**直接丢给 agent 的后果**：用教科书舒适的方法处理，但不知道你家从不烘衣机、衣服都要放洗衣袋。结果衣服缩水或出现荷叶边。

---

### Step 1：格式标准化（Format Standardization）

把 Human SOP 改成 agent 能够读懂的版本。

**三个重点**：

#### （1）参数化（Parametrize）

不要在 SOP 里写死，要用参数让 SOP 变成 template：

| 参数 | 可能值 |
|------|--------|
| `mode` | `quick` / `normal` / `delicate` |
| `temperature` | `cold` / `warm` / `hot` |

这样一份 SOP 就能 cover 各种场景。**SOP 一旦写死就没办法重复使用。**

#### （2）Must / Should / May 框架

源自 RFC 2119（原本用于网络协定的规格书），用来写 AGI SOP 超好用。强制把每一条规则的强度想清楚：

| 强度 | 含义 | 范例 |
|------|------|------|
| **must** | 硬性规定，agent 必须做，绝对不能跳过 | 先检查每一件衣服的洗标；把白色跟深色分开；启动洗衣机后等待完成 |
| **should** | 建议做法，有强烈理由可以不做，但要明确说明原因 | 根据衣物材质选择合适的洗衣模式；根据今天天气决定要不要用烘干 |
| **may** | optional，做不做都可以 | 湿度 > 70% 时使用烘干机，否则改用晾的方式 |

每一条规则的强度都很明确，agent 看到就知道哪些不能讨价还价，哪些可以根据 context 自己判断。

#### （3）结构化格式

用 Markdown 把区块切清楚，把 `Parameters` / `Steps` / `Error Handling` 等每个区块分开。既让人看得懂，也方便之后塞进 MCP 这类标准接口里，当成 agent 的行为规格。

> 处理完后，手上的东西就不再是一篇给人看的散文，而是一份 agent 真的读得懂的 SOP。

但光 SOP 写得漂亮还不够，只是把 Human SOP 翻译成 agent 能读的格式，**还没真的拆解任务**。

---

### Step 2：任务拆解与连接（Decompose & Connect）

把它拆解成 pipeline steps，每一个 step 都是 pipeline 里的独立节点。

**洗衣服拆解为四步**：

```
Step 1: 分类衣物
Step 2: 检查口袋
Step 3: 设定机器
Step 4: 决定要晾衣还是烘干
```

**每个步骤的关键特性**：
- 自己的 input
- 自己的 output
- 可以**独立执行、独立 debug、乃至独立替换**新逻辑

**为什么强调独立？**
如果分类衣物有 bug，把白色 polo 衫误判成深色衣物，只要修这一段就好，后面的设定机器、决定晾或烘的逻辑完全不用动。

如果是 mega agent 全部塞在一个 prompt，出错就只能整个重写，因为根本不知道是哪一段逻辑出问题。

**每个 step 可以变成小 skill / 小 agent**：

| Agent | 职责 |
|-------|------|
| Agent A | 只负责分类（input: 衣物列表；output: 分类结果） |
| Agent B | 根据分类结果决定洗衣机的 mode 和 temperature |
| Agent C | 判断天气，决定走晾干还是烘干 |

三个 agent 各自做一件很笨但超级明确的事，加起来就是一条完整的洗衣服 workflow。

**节点之间靠什么串接？答案是 Artifacts**

> 上一个 agent 的 output，变成下一个 agent 的 input

**分类 agent 输出范例**（JSON）：
```json
{
  "white": [...],
  "everyday": [...],
  "delicate": [...],
  "unstated": [...]
}
```

这份 artifact 直接变成设定机器 agent 的 input。设定机器的 agent 看到 JSON，根据规则决定每一批应该怎么洗，吐出一份洗衣服的设定，再交给下一个 agent。

**节点连接的三大要素**：
- 清楚定义的 input
- 清楚定义的 output
- 中间的 artifact 格式

### Step 3：双向开发（Bidirectional Development）

这是整个四步里**最重要的**，因为你的第一版 SOP **一定会有问题**。

#### 为什么第一版一定会出包？

先认识一个名词：**默会知识（Tacit Knowledge）**，又称内隐知识。

> 指那些难以用文字、言语或图表明确表达，存在于个人大脑与身体记忆中的知识。

SOP 的本质是把脑中的默会知识转成文字明确的规则。但默会知识的特性是：**你自己不会发现它的存在，直到它出错**。

你以为写完了，但脑子里还有十几条没写进去的判断标准，要等 agent 真的跑出去撞墙了、出错了，你才会发现"啊，原来这条我没写到"。

#### 双向开发的实际流程

```
1. 用自然语言跟 agent 说：我平常洗衣服大概是这样这样，请你帮我写一份 SOP
2. Agent 帮你写好第一版
3. 实际跑一次 workflow
4. 发现问题：把所有 T 恤都丢进超高温烘干机，结果缩水到穿不下
5. 回头补一条 SOP 规则：不可以把含棉量超过 80% 的衣物用高温烘干
6. 再跑一次，又发现新问题：没有把衣服装进洗衣袋
7. 再补一条 SOP
8. 不断重复，每轮 agent 都会踩到一个你没想过的坑
9. 几轮后 SOP 会稳定到能满足大多数使用情境
10. 剩下的 5% 是真正的 edge case，用 human-in-the-loop 处理

#### 实际案例对比

| 做法 | 结果 |
|------|------|
| 花两个月写完美 SOP | 跑一次就垮了，因为 cover 的全是想象中的情境 |
| 用敏捷精神：两天写粗糙版本 + 一周内跑 50 次 iteration | 两周内上线 |

**速度的关键不是写得多完美，而是迭代得有多快。**

> 你跟 agent 一起跑、一起 debug、一起 iterate，根据真实的执行结果持续修复迭代 SOP。

---

### Step 4：整合与执行环境（Integration & Runtime）

这一步决定你的 agent 到底是 demo，还是真的能在 production 跑。

**关键**：再漂亮的 SOP，如果没接到真实世界的工具，永远只是一份文件不会自己动起来。

| 场景 | 工具 |
|------|------|
| 洗衣服 | 洗衣机、烘干机、天气 API |
| 企业 agent | 内部系统、资料库、API、档案系统、版本控制、ticketing system |

**问题**：这些东西每家公司都长不一样，为 A 公司写的工具搬到 B 公司可能完全动不了。

## MCP：Model Context Protocol

### 是什么

**MCP 是一个开放协定**，目的是让 LLM agent 可以透过同一套标准去调用外部的 tools、resources、help prompts。

### USB-C 比喻

> MCP 就像 AI 世界的 USB-C

- 以前每出新设备都要买一堆转接线
- USB-C 出现后一条线全部统一
- 不管用 ChatGPT、用 Claude、用 cursor，只要支援 MCP，就能用同样的方式调用工具

### 实际效益

今天写好一个 Slack MCP server，明天 ChatGPT 跟 Claude 都能用，不需要为不同 host 各写一套整合。

### 产业采用现况

MCP 目前已被 ChatGPT、Claude、Cursor、各种 IDE 与 agent 平台采用。Anthropic 在 2025 年初把这个协定捐给 Linux Foundation 底下的 Agentic AI Foundation，意味着：
- 不再是某一家公司的私有规格
- 是有基金会背书、会长期维护的开放标准

**采用 MCP 的企业级产品**：
- ServiceNow：处理 IT、HR 请求、各种内部服务流程，都用 agentic workflow 而非传统规则引擎
- 其他大公司也都在产品线里把 agentic workflow 跑起来了

## Human-in-the-Loop Checkpoint

在整合阶段必须做的事：**设计人类把关的检查点**。

### 定义

在某些决策点，**agent 必须停下来，请人类确认**：
- 高风险的决策之前 → agent 要先停下来等人确认
- 大规模变更之前 → agent 要等人按 OK 才继续

### 为什么必要

任何 agent workflow 不管多成熟，总会有些 edge case 是 agent 没办法判断的。这时有两个选择：

| 选择 | 风险 |
|------|------|
| 让 agent 乱猜 | 风险很高 |
| 让 agent 停下来问人类 | 风险可控 |

整条 agent workflow 才不是黑箱、不是失控的机器，而是**人类掌舵、agent 执行的系统**：
- 你还是最后拍板的人
- 所有重复机械确定性的事都不用自己做了

## 实战案例：公司内部请求分类系统

### 场景设定

200 人公司，每天有人透过各种管道（表单、Slack、Teams、Email、私讯）丢杂事进来：

> "我要申请新系统的权限"
> "这张发票可不可以报账？"
> "我下礼拜要 onboard 一个新同事，他需要哪些工具的存取？"

### 原始 Human SOP

1. 打开内部 ticket 系统
2. 扫一眼描述，判断是 IT 问题、权限申请、HR 需求、财务报账还是其他类别
3. 补上 priority 和 deadline
4. 根据规则 assign 给对的 team 或对的人
5. 如果写得很模糊 → 回信问清楚（例：「你说电脑很慢，是开机慢还是某个系统很卡？」）

流程不复杂但很烦、很重复、每天都要做，**最适合给 agent 处理**。

### Step 1：标准化 SOP（`internal_request_triage`）

**Parameters**：
- `ticket 来源`
- `原始文字`
- `员工编号` 等

**Steps**（must/should/may）：

```markdown
## must
- 先根据员工编号验证这个人是不是在职员工
- 根据 ticket 内容，把请求分类成 IT / HR / Finance / Other 这 3 类
- 根据 SLA 规则和关键字判断 priority 是 high / medium 还是 low
- 产出一份结构化输出，包含 category、priority 等栏位
- 如果"是否需要澄清"栏位是 true，agent 必须再产出 2-3 个需要问使用者的问题
```

**已完成**：有明确的 must/should、有可重复使用的 parameters。这就是 step 1 做的事。

### Step 2：拆解为两个 Skill

| Skill | Input | Output | 职责 |
|-------|-------|--------|------|
| `internal_request_triage` | ticket 文字 | JSON（category、priority、推荐 assignee、是否需澄清） | 专门做分类判断、priority 推荐、assignee 推荐 |
| `internal_reply_drafting` | 第一个 skill 的 JSON output | 给同事的回复草稿 | 根据 triage 结果产生回复，告知处理人、预估回复时间 |

**两个 skill 各做各的事，靠 JSON artifact 串起来**：
- triage 失败 → 不影响 reply drafting 的逻辑
- reply drafting 改时 → 不需要动 triage 的分类逻辑

### Step 3：双向开发

写完第一版后跑一次，**一定**会发现问题：
- 某类请求一直被误分类成 Other
- priority 永远都判 medium
- assignee 老是推荐给已经离职的人

**没关系**，回头改 SOP、补一条规则、再跑一次、再改。3-5 轮后，整个区决的准确度会趋于稳定。

### Step 4：整合与执行

**接到真实系统**：加一个小 script，把 triage 结果写回公司内部的 tracking sheet（Notion / Jira / Google Sheet 等）。

**Human-in-the-Loop Checkpoint**：在高风险请求前加 checkpoint：
- 涉及财务超过 5000 块的请求
- 涉及资安权限变更的请求
- **agent must 停下来等人按 OK**

### 完整流程

```
读 ticket → 自动分类 → 产生回复草稿 → 写回追踪系统 → 必要时请人确认
```

一份原本只能给人跑的 SOP 变成一条**每天自动跑、出错能第一时间知道怎么修**的 workflow。

## 落地行动建议

不要一次把公司所有流程都变成 agent workflow，会把自己搞死。

### 具体做法

1. **挑一份**手上最无聊但一直在重复做的 Human SOP：
   - 每周周报
   - 每次 release 的 checklist
   - 新人 onboarding 固定流程
   - 挑你最不想做的那个
2. **照着四步走一遍**
4. **不用一开始就完美**，也不用一开始就完全自动化
5. **先有一个跑得起来的、能听你话 30% 的版本**，再慢慢迭代

---

## 核心心法

> **你不是在学怎么用 AI，而是在学怎么设计给 AI 用的工作流。**
> 前者半年就会过时，后者越来越值钱。

在 MCP、agent workflow、multi-agent 系统越来越普及的世界，**能把流程拆好、设计成 agent 真的能执行的 workflow，这种能力的价值只会越来越高**。
